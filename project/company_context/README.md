# Бизнес-контекст компании — задача 1

## Дополнительные показатели платёжного окружения

В `payment_summary.counterparty_context` передаются раздельные блоки `in` и `out`:

- `industry_distribution`: суммы и доли по двухзначным подразделениям ОКВЭД
  контрагентов и укрупнённому сектору. Строка с `okved_division: null` явно
  показывает поток с неизвестной отраслью.
- `group_distribution`: `same_group`, `other_group`, `unknown`. Сравнение известно,
  только если у обеих компаний есть непротиворечивый `GROUP_ID`. Отсутствующая
  группа не считается доказательством внешнего платежа. Общие физлица не
  подменяют идентификатор группы.
- `coverage`: отдельно для карточек компаний (`company_card`), отраслей
  (`industry`) и групповой принадлежности (`group_membership`) показаны известная
  и неизвестная суммы, а также доли от полной суммы направления.

В знаменателе всегда весь наблюдаемый входящий или исходящий поток, включая
неизвестных контрагентов. Ограничение `top_n` не влияет на расчёты. В каждой
категории показываются до 20 ID для проверки, их полное количество и признак
усечения. Все суммы считаются по всем связям. При нулевом потоке доли равны
`null`; при отсутствии источника платежей блоки `in/out` целиком равны `null`.
Источники, поля объединения и метод расчёта находятся в `evidence`, хеши исходных
файлов — в общем `provenance.sources`. Снимок базы пересобирать не требуется.

Отрасль с долей не менее 25% получает объяснимый сигнал значимости. Версия правил
сигналов — `deterministic_rules_v2`. Прежние профили v1 допустимы по контракту;
новый блок добавлен как необязательное поле схемы 1.0 для совместимости.

Эти показатели не являются оценкой автономии, ликвидности или вероятности убытка.
Назначения платежей, валюты, период и договорные роли по-прежнему неизвестны.

Для просмотра в интерфейсе: «Подготовить контекст» →
`data.input.profile.payment_summary.counterparty_context`.

Модуль преобразует три CSV приложения 1 в воспроизводимый профиль компании для
отбора новостей и AI-интерпретации. Работает локально на SQLite, без Docker,
сторонних Python-библиотек, сетевых запросов и расходования LLM-бюджета.
Python 3.10+, проверено на Python 3.13. Запускать команды из корня репозитория.

## Быстрый запуск

В Windows с существующим виртуальным окружением можно заменить `python` на
`.\.venv\Scripts\python.exe`.

```powershell
python -m company_context build --companies data/appendix_1/df_Uid_data_hack.csv --links data/appendix_1/df_Fid_Uid_link_hack.csv --payments data/appendix_1/df_Uid_payment_hack.csv --database data/processed/company_context.sqlite --report data/processed/dataset_audit.json
python -m company_context list --database data/processed/company_context.sqlite --limit 10
python -m company_context profile --database data/processed/company_context.sqlite --company-id U_67 --output data/processed/company_profile.json
python -m company_context audit --database data/processed/company_context.sqlite
python -m unittest discover -s tests -v
```

Команда `build` однократно загружает CSV и создаёт индексы. После изменения
исходников её нужно выполнить снова. База заменяется только после успешного
построения; открытые читатели в Windows должны быть закрыты перед заменой.
`profile` работает с готовым снимком и не перечитывает CSV.
`--links` и `--payments` можно опустить: в профиле будет отмечено отсутствие
источников. `--top-n` (по умолчанию 20, максимум 1000) ограничивает выдачу связей,
но суммы платежей, концентрация и численность группы считаются по всем данным.
Списки имеют индикаторы усечения. `profile` без `--output` печатает JSON.

**Единицы выручки требуют подтверждения.** ТЗ называет поле годовой выручкой,
но явно не задаёт единицу измерения. По умолчанию `--revenue-unit unknown`:
исходное значение и сравнение в выборке доступны, `revenue_rub` и признак
крупного бизнеса равны `null`. После подтверждения единиц перестройте базу с
`--revenue-unit rub` или `--revenue-unit thousand_rub`. Только тогда доступен
`list --large-only`; критерий — строго больше 15 млрд рублей.
У валюты и периода платежей также нет подтверждённого значения.

## Python API для AI/Backend

```python
from company_context import ContextStore, build_database

# Обычно build_database вызывается один раз отдельной командой.
with ContextStore("data/processed/company_context.sqlite") as store:
    company_profile = store.get_company_profile("U_67", top_n=20)
    audit = store.metadata["audit"]
```

`ContextStore` открывает базу только на чтение. Создавайте отдельный экземпляр
на поток/запрос либо используйте его последовательно; SQLite connection не
предназначен для совместного использования несколькими потоками по умолчанию.
Неизвестный ID вызывает `KeyError`, неверный параметр — `ValueError`.
CLI возвращает код 2 и понятное сообщение при ошибке.

## Контракт профиля 1.0

Машиночитаемая структура описана в `profile.schema.json`. Основные поля:

| Поле | Содержание |
|---|---|
| `company_id`, `schema_version` | Синтетический ID и версия контракта |
| `industry` | Исходный ОКВЭД, название, двухзначное подразделение и укрупнённый сектор |
| `scale` | Исходная выручка, единицы, рублёвая выручка при известных единицах, работники ФНС/СПАРК |
| `company_attributes` | Возраст, стадия развития, тип организации, собственность, клиентский статус, исходный признак ключевого собственника |
| `bank_products` | РКО, гарантии, кредиты, лизинг, депозиты, зарплатный проект, факторинг |
| `foreign_trade` | Признак наличия сведений ФТС и страны; направление торговли и валюты неизвестны |
| `geography` | Регион и город регистрации |
| `dataset_position` | Место по выручке внутри двухзначного ОКВЭД, медиана, процентиль и доля наблюдаемой выручки |
| `group` | Наблюдаемые члены группы и неконсолидированная сумма их выручки |
| `related_companies` | Компании с общими физлицами, количество общих людей и источники |
| `counterparties` | Направление, сумма, количество, доля в потоке, отрасль контрагента и источники |
| `payment_summary` | Полные итоги входящих/исходящих платежей, крупнейшая доля, top-5 и HHI |
| `relevance_signals` | Темы для ранжирования с объяснением, весом, сущностями и JSON Pointer на признаки |
| `data_quality` | Пропуски и предупреждения, включая противоречия |
| `provenance` | Исходная карточка, CSV-записи, имена и SHA-256 файлов, версия правил, время снимка |

`null` означает неизвестное значение и отличается от `false` и нуля.
Сигналы — результат детерминированных правил, а не аналитическая позиция банка
или подтверждение будущего ущерба. `weight` — эвристический приоритет 0..1,
не вероятность. Он требует последующей настройки на оценке качества ранжирования.
`evidence` содержит JSON Pointer, например `/bank_products/loan`.
Его можно разрешить в профиле и сопоставить с исходными полями в
`provenance.company_raw_fields` и записью `provenance.company`.
Правила находятся в `signals.py`; LLM не используется.

## Расчёты и ограничения

- Отрасль определяется по основному ОКВЭД. Дополнительные виды деятельности
  не выдумываются: их нет в исходных столбцах. Сектор — укрупнённое правило
  по диапазонам подразделений, а не внешний официальный справочник.
- Положение рассчитывается только внутри предоставленной выборки одного
  двухзначного ОКВЭД. Ранг = 1 + количество компаний с большей выручкой;
  при равенстве ранги совпадают. Процентиль — доля известных выручек <= текущей.
  Доля наблюдаемой выручки = выручка компании / сумма известных выручек этого
  подразделения. **Рыночная доля не вычисляется**: знаменатель рынка отсутствует.
- В сумме выручки группы возможен внутригрупповой оборот; это не
  консолидированная выручка. Члены вне выборки неизвестны.
- Платежи хранятся с десятичными значениями и суммируются через `Decimal`.
  JSON выводит числовые значения; потребителям с требованиями к финансовой
  точности следует учитывать ограничения чисел JSON/JavaScript.
- Повторные строки платежей складываются. Без идентификатора операции
  нельзя отличить дубль выгрузки от дополнительного агрегата. Самоплатежи
  исключаются из графа внешних контрагентов с записью в аудит.
- Доля контрагента считается отдельно по входящему/исходящему потоку до
  усечения списка. HHI = сумма квадратов долей, диапазон 0..1;
  при нулевой сумме доли и HHI неизвестны (`null`).
- Получатель платежей не обязательно поставщик, отправитель не обязательно
  покупатель. Общий человек не доказывает владение и контроль. В таблице связей
  нет роли физлица; сведения о его месте проживания не становятся географией бизнеса.
- ФТС не доказывает импорт, экспорт, валюту операций или экономическую
  зависимость от страны. При конфликте флага и стран автоматический торговый
  сигнал не формируется, конфликт сохраняется в `data_quality`.
- Пропуски работников не заменяются нулём. ФНС используется первой для
  общего диапазона, СПАРК — запасным источником; оба значения сохраняются отдельно.

## Качество и трассировка

Загрузчик поддерживает UTF-8/BOM, CP1251, разделители `;`, `,`, tab, кавычки,
пробелы в числах и десятичную запятую. Номера записей логические, заголовок = 1;
они могут отличаться от физических строк, если в CSV есть многострочные поля.
Отсутствующие ID и невалидные платежи исключаются с подсчётом причин.
При дубликате ID компании сохраняются все исходные карточки в `company_variants`.
Поля с разными значениями становятся `null` и не участвуют в отраслевых или
финансовых расчётах; совпавшие значения сохраняются. Конфликтующие поля и
варианты доступны в профиле, исходные записи — в SQLite. Повторные связи человек-компания
схлопываются. Неизвестные контрагенты остаются в графе с отсутствующей карточкой.
Аудит содержит число строк, пропуски, число ошибок по типам, до 50 примеров
и число участников без карточки. В профиле доступен до 20 номеров исходных
записей на связь; флаг усечения и общее число позволяют запросить полные данные
из таблицы SQLite по компании/направлению и проверить их по исходному CSV.

База SQLite, аудит и выгрузки помещаются в `data/processed/`, которая исключена
из Git. Для проверки без исходных данных есть маленькие синтетические CSV
в `tests/fixtures/company_context/`. Приложение 2 относится к последующему
RAG/интерпретации и на этом этапе не загружается.

## Проверка на предоставленном наборе

Обработаны 85 525 строк компаний (85 514 уникальных ID), 12 514 связей
и 1 380 585 строк платежей. 27 406 самоплатежей исключены из внешнего графа,
1 353 179 строк платежей сохранены. У ID `U_428697` обнаружены 12
противоречивых карточек: спорные значения не выбираются автоматически.
У 114 552 участников платежей и 7 788 компаний из таблицы связей нет карточки
в наборе компаний; это ограничение покрытия, а не основание удалять связи.
Прошли 19 тестов и проверка 100 случайных профилей на сериализацию и
разрешимость ссылок evidence. Примеры: `U_9250`, `U_57706`, `U_258064`
и конфликтующий `U_428697`. Числа относятся к снимку с SHA-256 из аудита.
