# Данные для обучения эффекта действий

В исходных CSV нет истории «предприниматель выбрал действие → получил результат». В этом пакете **0 таких наблюдений**. AI-советы в `analysis_targets.jsonl` описывают возможные следующие шаги и вопросы; они не являются целевыми значениями для регрессии экономии или коэффициентов эффективности.

Контракт записи находится в `action_observation.schema.json`. Собирать следует один эпизод решения: компания, связанные события, дата решения, снимок состояния, доступные варианты, выбранные действия с дозами, условия выбора, период результата, реально измеренные показатели и источники. Запись с `outcome=null` допустима как ожидающая результата, но не как обучающая строка с нулевым эффектом.

Нужно сохранять также случаи без действия (`chosen_actions=[]`) и неудачные результаты. Дозы выражать в явных единицах: доля открытой валютной позиции, дни запаса, рубли финансирования. Стоимость и потребность в ликвидности — разные поля. Несколько действий одного решения принадлежат одному эпизоду, их нельзя представлять независимыми наблюдениями с одинаковой прибылью.

Показатель результата задаётся до выбора действия: например, валовая прибыль в рублях за 30 дней с единым правилом расчёта. Отдельно сохранить стоимость действий, сезонность, отрасль, исходную экспозицию, действующие хеджи, ограничения бюджета, изменения спроса и другие решения. Снимок и предлагаемые варианты должны быть доступны **до** `decision_at`; результат — после. Не включать будущие факты в признаки.

Наблюдаемая прибыль после действия не сообщает, что произошло бы без него. Предположение о результате «без действия» хранить отдельно от наблюдений и не называть фактом. Обычный МНК на наблюдениях «до/после» может перепутать действие с причиной его выбора. Для причинного эффекта нужен подходящий дизайн сравнения: например, контролируемый эксперимент для допустимых вариантов или обоснованная оценка по наблюдательным данным с контролем исходных различий. Само наличие поля propensity не устраняет смещение.

`assignment.propensity` — вероятность выбора **всего наблюдаемого плана**, только если она реально известна из механизма назначения; иначе null. Не подставлять туда предсказание ранжировщика новостей. У непрерывных доз нужны отдельно заданные модели плотности назначения — вероятность точной дозы не заменяется произвольным числом.

После накопления данных обучение должно разделять компании и эпизоды по времени, исключать незавершённые/повреждённые наблюдения и фиксировать пропуски. Сначала оценить модель результата при заданных действиях и её неопределённость на отложенных наблюдениях. Только затем оптимизировать доступные действия при фиксированных обученных коэффициентах. Минимизировать сами коэффициенты для получения минимального убытка нельзя: это разрушает модель вместо выбора решения.

Схема проверяет структуру записи. При загрузке дополнительно проверить: `snapshot.observed_at <= decision_at`, начало результата не раньше решения, конец не раньше начала, уникальность ID эпизода и действий, выбранные ID входят в список доступных, дозы не превышают доступные, валюты и единицы согласованы. Фактические наблюдения хранить в защищённом хранилище проекта; в публичный репозиторий достаточно коммитить схему и обезличенные допустимые данные.
