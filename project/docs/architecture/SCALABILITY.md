# Масштабирование и сопровождение

> Критерий успеха №7 ТЗ: решение предусматривает масштабирование на новые отрасли, типы клиентов и источники данных, а также описывает подход к дальнейшему техническому сопровождению. Этот документ показывает, за счёт чего система расширяется и как её поддерживать.

## Принцип: расширение данными и правилами, а не переписыванием кода

Система устроена так, что новые отрасли/клиенты/источники добавляются **конфигурацией и данными**, не меняя архитектуру. Контракты (`contracts/v1`) фиксируют интерфейсы, поэтому компоненты расширяются независимо.

## 1. Новые отрасли

**Что уже помогает:** отрасль определяется из кода ОКВЭД (`company_context`), укрупнённый сектор — по диапазонам подразделений. Любая компания с валидным ОКВЭД сразу получает отрасль и сектор — новые отрасли не требуют кода.

**Точки расширения:**
- Сопоставление «тип события ↔ отрасль» в правилах сигналов (`news_analysis`, `conditional_advice`) — добавить отраслевые эвристики.
- RAG-корпус: добавить отраслевые материалы банка (новые PDF) — индекс перестраивается, код не меняется.
- Проверка охвата: прогнать метрики (`evaluate_ranking.py`) на компаниях новой отрасли.

## 2. Новые типы клиентов

- Профиль уже описывает клиента признаками (размер, продукты, ВЭД, группа, роль пользователя CFO/CEO/казначейство), а не хардкодом «одной компании».
- Новый тип клиента = новые значения признаков, которые ранжирование и промпты уже учитывают.
- Роли интерфейса меняют акценты интерпретации без изменения прав доступа (см. `SECURITY.md`).
- Для среднего бизнеса и т.п. — те же контракты, другой порог «крупности» (конфиг `--revenue-unit`/порог).

## 3. Новые источники данных

- **Новости:** источники RSS/HTML задаются конфигом (`NEWS_FEEDS_JSON`); добавление ленты не требует кода. Сбой одного источника не останавливает остальные (заложено в задачах роли 3).
- **Аналитика банка:** новые документы → OCR/чанки → индекс; версия корпуса версионируется.
- **Данные компаний:** загрузчик CSV устойчив к кодировкам/разделителям/грязным данным; новые поля добавляются в профиль аддитивно.
- Все источники проходят через нормализацию в контракт `Event`/`Profile`, поэтому потребители не меняются.

## 4. Техническое масштабирование (нагрузка)

- **Профиль/граф:** предрасчёт в SQLite с индексами; `build` однократный, чтение профиля — быстрые запросы, не перечитывает CSV.
- **RAG:** эмбеддинги считаются один раз и кешируются; переход на векторную БД (Qdrant/pgvector) для больших корпусов — по контракту, без смены агента (R3-05).
- **Агент/LLM:** кеш анализов (повтор без платного пересчёта), очередь задач, лимиты параллелизма; маршрутизация моделей по сложности (дешёвая для классификации, дорогая для интерпретации) — под бюджет.
- **Сервисы разделены** по HTTP (Python ranking, Node agent/retrieval, gateway) — масштабируются независимо.

## 5. Управление стоимостью при росте

Масштабирование упирается не только в нагрузку, но и в **бюджет LLM**. Механизмы:
- Правила и предрасчёт (профиль, сигналы) не тратят токены — основная фильтрация бесплатна.
- LLM вызывается только на финальной интерпретации отобранных событий.
- Кеш + маршрутизация моделей + лимиты токенов; контроль расхода — `scripts/estimate_budget.py`.

## Подход к сопровождению

| Область | Практика |
|---|---|
| Контракты | версионируются (`contracts/v1`); изменения — через новую версию и переходный период, не «тихо» |
| Качество | метрики на каждый PR (`evaluate_ranking.py`), пороги в `MONITORING.md` |
| Корпус/модели/индекс | версионируются; инвалидизация кеша при смене корпуса |
| Данные | provenance (SHA-256, номера записей) — воспроизводимость снимков |
| Проверки | typecheck + test + build (Node), unittest/pytest (Python); CI без платных вызовов |
| Секреты/бюджет | `.env`, лимиты, мониторинг расхода (см. `SECURITY.md`) |
| Документация | решения в `DECISIONS.md`, роли и границы в `docs/integration/TEAM.md` |

## Честные ограничения
- Переход на векторный/гибридный RAG ещё не выполнен (R3-05) — на больших корпусах лексического поиска не хватит.
- Аутентификация и пер-пользовательские квоты бюджета — для продакшена (прототип без них).
- Отраслевые эвристики пока базовые; расширение требует экспертной настройки и переизмерения метрик.
