# Проверка генерации и источников

Промпт `company-news-grounded-v6` находится в `server/integration/analysis-prompts.ts`. Внешняя LLM получает инструкции отдельно от недоверенных текстов новости, профиля, цитат и вопросов. Для CFO/CEO/казначейства задаётся аудитория. Факты, условные выводы, действия, неизвестные данные и ограничения разделены.

## JSON ответа

`GeneratedAnalysis` содержит `summary`, `why_relevant`, `claims`, массивы `risks`, `opportunities`, `recommendations`, `limitations`, `missing_data` и объект `grounding`. Модель не устанавливает ID, источники, режим и время: это делает сервер. Генератор схем — `scripts/build_contracts.py`, общие определения — `contracts/v1/schema.json`, маршруты — `openapi.json`.

| Поле | Основание |
|---|---|
| `claims[].kind=fact` | `text=quote`, точная цитата минимум 8 символов из выбранного news-excerpt |
| `claims[].kind=bank` | `text=quote`, точная цитата из выбранного датированного bank-excerpt |
| `claims[].kind=ai` | `quote=""`, ID выбранных company и news, конкретные `profile_paths`, непустые `conditions` |
| `grounding.summary` | Индексы claims, включая fact |
| `grounding.why_relevant` | Индексы claims, включая ai |
| `grounding.risks/opportunities` | Отдельный массив индексов claims для каждой строки |
| `grounding.recommendations` | По одному `{claim_indexes,condition,required_data}` на рекомендацию |

Индексы считаются с нуля. Например: `"profile_paths":["/bank_products/loan"]`, `"conditions":["Если ставка договора меняется"]`. В рекомендации необходимы условие и данные, которые нужно проверить. Ссылаться на весь профиль, `provenance`, неизвестный путь или целый объект нельзя. `false` и `0` не считаются пропуском. Ссылка на `null`/`unknown` требует явных `missing_data` и `limitations`.

Тексты действий находятся только в `recommendations`, основания — в `grounding.recommendations`, в том же порядке и количестве. Пример связанных полей (при `claims[0].kind="fact"`, `claims[1].kind="ai"` и соответствующем `claims[1].conditions`):

```json
{
  "recommendations": ["Уточнить договорную экспозицию компании"],
  "missing_data": ["Условия договоров"],
  "grounding": {
    "summary": [0],
    "why_relevant": [1],
    "risks": [],
    "opportunities": [],
    "recommendations": [{
      "claim_indexes": [1],
      "condition": "Если договоры компании предусматривают изменение ставки",
      "required_data": ["Условия договоров"]
    }]
  }
}
```

Это фрагмент, а не полный ответ. `grounding` содержит ровно пять показанных полей; `limitations` и `missing_data` разрешены только на верхнем уровне. Объекты вместо строк в `recommendations` и дополнительные поля в `grounding` отклоняются. При отсутствии действий оба массива рекомендаций пусты.

При `LLM_RESPONSE_FORMAT=json_schema` схема для провайдера строится из тех же канонических определений в `server/integration/response-schema.ts`. Для strict-формата fact/bank и ai представлены отдельными ветвями `anyOf`, без добавления `null` в необязательные поля. `uniqueItems` не передаётся в ограниченное подмножество схемы провайдера; исходный локальный контракт продолжает проверять уникальность. Локальные структурные проверки, цитаты, индексы, условия и источники проверяются в обоих режимах без изменений. Формат strict Structured Outputs: [документация OpenAI](https://developers.openai.com/api/docs/guides/structured-outputs).

Проверяются JSON, существование источников и полей, дословность цитат, привязка к выбранной компании/новости/дате, наличие условий, полнота индексов, отсутствие неиспользуемых claims. Числовые литералы в выводах и разделах должны находиться в связанных фрагментах или выбранных значениях профиля. Без RAG сервер добавляет сообщение об отсутствии банковских материалов, при синтетических данных — соответствующую пометку. Gateway повторяет проверки на собственном контексте и сравнивает источники с оригиналами.

Текстовые разделы не могут состоять только из пробелов. Все источники, указанные для одной дословной fact/bank-цитаты, должны содержать её. При числовой проверке учитывается знак; цифры внутри company ID не являются финансовым основанием. Хэш контекста не зависит от порядка ключей JSON.

При нарушении структуры/оснований допускается одна повторная генерация из того же исходного контекста, затем выдаётся ошибка. Ошибки авторизации, квоты, транспорта, отказ модели, превышение размера и обрезанный ответ не вызывают автоматический повтор платного запроса. Тело ошибки провайдера и ключ пользователю не возвращаются.

## Исправление ответа и диагностика

Лимит остаётся прежним: начальная генерация и **одно исправление**, максимум два вызова. Перед исправлением сохраняется запись в SQLite роли 2, таблица `llm_rejected_drafts`. Модель получает исходный контекст, проверенные ошибки полей и структурный снимок предыдущего черновика. Невалидный ответ не превращается в готовый анализ и не попадает в историю анализов.

Примеры ошибок:

- `/recommendations/0: Expected type string` — вместо строки вернулся объект;
- `/grounding/limitations: Unexpected field` — поле отсутствует в контракте grounding;
- `/grounding/recommendations/0/condition` — условие не совпадает с conditions связанного ai-claim;
- `/grounding/recommendations/0/required_data` — данные отсутствуют в missing_data;
- `/claims/0/quote: Quote not found in selected evidence` — цитата не найдена во всех указанных источниках;
- `/claims/1/profile_paths/0: Unknown profile path` — путь не существует в профиле.

Для уточняющих вопросов пути относятся к реальным полям `answer` и `claim_indexes`, а не к внутреннему представлению анализа. Ошибки структуры содержат JSON Pointer, правило и ожидаемый тип (при ошибке типа); для численных границ схемы передаётся `limit`. Grounding сообщает первый конкретный отказ и путь поля. До 10 структурных ошибок передаются за одну попытку.

При окончательном отказе `Error.error.diagnostics` содержит `issues`, случайный `generation_id`, `attempts`, `max_attempts=2` и `draft_saved`. Те же данные проходят через HTTP-клиент интеграции до браузерного SDK. Интерфейс `/analysis/` и продуктовый `/v1`-адаптер показывают причину, ID диагностики и сбой сохранения снимка, если он произошёл. При успешном исправлении ссылка на диагностику добавляется в `trace` как `response_repair`. CLI-оценка и tuning harness сохраняют диагностику в отчёт неуспешного live-сценария. Лимит `llm:tune --max-calls` учитывает возможный repair и не превышается вторым вызовом. Если второй вызов завершился транспортной ошибкой, её код и безопасное пояснение сохраняются вместе с диагностикой предыдущего отказа; третьего вызова нет.

`snapshot` — **структурный снимок, а не дословный ответ**: свободный текст заменён на `[string]`, числа на `[number]`, имена неизвестных полей заменены их количеством. Сохраняются известные поля схемы, типы и разрешённые enum-значения. Для непарсируемого JSON сохраняется только `[unparseable]`. Исходный ответ, ключ, HTTP-заголовки, тело ошибки провайдера, профиль и исходный промпт не сохраняются в этой таблице и не добавляются в диагностику. Снимок ограничен глубиной 12, 30 элементами массива и бюджетом обхода 250; остаются последние 100 записей на базу, включая исправленные случаи. В API снимки не передаются. Удаление записей не меняет счётчик платных вызовов.

Для локального разбора найдите строки по `generation_id` из ошибки или `trace`:

```sql
SELECT attempt, contract, snapshot, diagnostics, created
FROM llm_rejected_drafts
WHERE generation_id = ?
ORDER BY attempt;
```

Правила диагностики перечислены в общем allowlist `contracts/diagnostic-rules.json`. Сервер не возвращает сырые сообщения Ajv, значения полей, неизвестные имена ключей и сообщения модели. Контракт ошибки допускает только эти правила, ограниченные типы и числовые границы; клиент повторно фильтрует диагностику и проверяет request ID. Основные JSON-контракты ответов и условия grounding не ослаблены. Воспроизводимые проверки с поддельным провайдером: `server/integration/tests/diagnostics.test.ts`; они не доказывают качество реальной LLM.

| Код | HTTP | Действие |
|---|---|---|
| `MODEL_AUTH_ERROR` | 502 | Проверить локальный ключ и доступ к модели |
| `MODEL_LIMIT` | 429 | Проверить локальный лимит и ограничения провайдера |
| `MODEL_TIMEOUT` | 504 | Повторить позже либо изменить timeout |
| `MODEL_UNAVAILABLE` | 503 | Проверить соединение/адрес и состояние провайдера |
| `MODEL_RESPONSE_INVALID` | 502 | Просмотреть причину проверки, параметры длины и модель |
| `CONTRACT_VIOLATION` | 502 | Исправить поставщика, который нарушил общий контракт |

## Уточняющие вопросы

`POST /v1/analyses/{id}/questions` использует сохранённый анализ, его источники, исходные `as_of`/`audience_role` и последние 10 пар реплик. Live-ответ дополнительно содержит `claims`, `claim_indexes`, `limitations`, `missing_data`: он проходит те же проверки цитат, полей и условий. Новых источников из истории разговора не появляется. Чужая компания не получает эту сессию. Сессии ограничены памятью gateway, 1 часом и 100 анализами; одновременно выполняется максимум два запроса к агенту.

## Границы проверки

Дословность цитаты подтверждает соответствие переданному тексту, а не правдивость первоисточника. Наличие поля и ссылки не доказывает причинную связь, корректность единиц, финансовую применимость или отсутствие противоречия. Проверка числовых литералов не понимает числа словами и экономические расчёты. Сам промпт не доказывает устойчивость модели к внедрённым инструкциям. Для этого нужны реальные ответы и содержательное ревью по [LLM_EVALUATION_UI.md](LLM_EVALUATION_UI.md).

Старый `/api` и демонстрационные ответы сохраняют исходные форматы. Усиленный контракт обязателен для `Analysis.mode=live` на новом `/v1`; новые поля необязательны для mock/demo. Это согласованное ужесточение live-границы: внешним реализациям роли 2 нужно обновиться вместе с контрактами.


## Числовые факты и repair v5

`summary` рекомендуется составлять только из целых дословных `fact.quote` (при необходимости также `bank.quote`), соединённых переводом строки. Ставка, сумма, дата, год, номер стандарта и ОКВЭД не переформатируются и не берутся из metadata. Наличие даты в `published_at` не даёт основания добавить её к цитате заголовка. AI-пояснения и применимость к компании выносятся в соответствующий AI-раздел без числовых финансовых прогнозов.

`response_guidance` передаётся модели при первоначальной генерации и исправлении: максимум одна дословная непрерывная цитата news и одна bank длиной не более 900 символов. Пример факта включает `text=quote`, разрешённый `source_id` и форму привязки индекса. Это фрагмент, не готовый анализ; для вопроса используется форма `answer/claim_indexes`. Примеры не строятся из невалидного текста модели, не добавляют новые источники и не меняют результат автоматически. Если нет короткой целой цитаты либо она содержит известный ключ/credential-подобный текст, пример пропускается. Инструкции из текста источника не получают системного статуса.

Для prepared-генерации тот же валидатор работает в режиме сбора до десяти независимых нарушений. Недействительная ссылка/claim блокирует зависимые проверки, но не скрывает нарушения других разделов и required_data. Все прежние условия принятия сохранены; функции извлечения чисел и распознавания финансовых показателей не изменены. Обычная проверка первого отказа по-прежнему доступна шлюзу.

`repair_rules` сопоставляет проверенному коду ошибки понятное правило исправления; рядом передаются допустимые цитаты и контрольный список индексов, условий и missing_data. `previous_violations` содержит историю уже выполненных проверок. Вторая версия полностью проверяется заново, поэтому исправленная дата не маскирует новую ошибку условия. В окончательной диагностике `issues` — текущие ошибки, `history` — не более двух попыток по десять ошибок. Исправленные прошлые ошибки не выдаются за текущие. История проходит тот же allowlist и хранится со структурными снимками; свободный текст модели в неё не включается.

Число платных попыток не изменилось: максимум два вызова. Примеры, сбор ошибок и повторная локальная проверка не вызывают LLM. HTTP/auth/quota/timeout/refusal/truncation по-прежнему не вызывают слепого repair. Канонические контракты GeneratedAnalysis/GeneratedAnswer и provider JSON Schema не ослаблены; контракт ResponseDiagnostics расширен необязательной history. Обновляйте сервис роли 2 и gateway с общей версией контрактов.

Воспроизводимые проверки: `server/integration/tests/numeric-repair.test.ts`, fixture `tests/fixtures/llm_numeric_regressions.json`. Три описанных пользователем сбоя реконструированы: дословные ответы прогона не были переданы. Используются сохранённые профили U_34911/U_99262 и реальные reviewed-публикации ЦБ/Минтранса, при подставных rank/LLM. Это регрессия протокола, не новый замер успешности внешней модели и не оценка точности продукта.


## Задачи 8–10: проверенные пути, одинаковые цитаты и осторожные отрицания

`response_guidance.profile_path_index` — справочник из максимум 64 проверенных путей (жёсткий предел helper — 128), без копирования значений профиля. У каждого пути есть type, unknown и связанные coverage_paths. Обход ограничен глубиной 14, 4000 узлами и первыми тремя элементами массивов объектов; truncated явно сообщает неполноту. Каждый предлагаемый путь проверяется тем же profileValue. Объекты и массивы объектов целиком, source/evidence/limitation, методические поля и служебные свойства массивов не предлагаются. Отсутствие пути в справочнике не означает ноль или отсутствие связи. Валидатор остаётся источником правил; индекс — ограниченный набор пригодных примеров, а не новый механизм доступа к данным.

Для листа industry_distribution требуется coverage.industry.known_share и unknown_share того же направления, для group_distribution — coverage.group_membership. Пары включаются в индекс вместе со статистикой и проверяются в AI-claim. Целый массив, объект строки, несуществующий индекс, произвольное поле или coverage другого направления отклоняются. null/unknown явно обозначены, false/0 сохраняются как известные значения. Модель не должна копировать весь индекс в profile_paths: выбираются только необходимые пути в рамках прежнего лимита двадцать.

`quote_candidates[].claim` для news и bank строится из одной выбранной подстроки: одна и та же строка копируется в text и quote. AI-пересказ — отдельный claim. Это проверенный пример формы для модели, а не автоматическая перезапись её ответа. Если модель всё равно возвращает пересказ в text или вымышленную quote, прежние проверки отклоняют ответ, после одной попытки repair возвращается точная диагностика. Даты и числовые правила предыдущего пакета сохраняются.

`ranking_evidence` вычисляет признак freshness_only_confirmed по всем ненулевым contribution, включая отрицательные, очень малые и взаимно компенсирующиеся строки. В модели показывается до 64 строк, но признак и count считаются по полному списку; наличие иных вкладов за этим пределом не скрывается. При отсутствии таблицы или одних нулях исключительно свежестное объяснение не подтверждено. Это описание предоставленной декомпозиции, не доказательство причинного эффекта.

Промпт v6 использует «Связь не подтверждена предоставленными данными». Узкий лексический guard проверяет распространённые категорические отрицания связи и неподтверждённое объяснение только свежестью в AI-claims, разделах, условиях, заметках и вопросах. Дословные fact/bank-цитаты в разделах исключаются из этой проверки. Квалифицированные формулировки неопределённости и условные фразы разрешены. Это не универсальная семантическая проверка и не доказательство корректности вывода.

Давний банковский источник не удаляется только из-за возраста, если он допустим по as_of. У bank-примера сохранена дата и оговорка: исторический фрагмент не равен текущей позиции банка. Доставка фрагмента, наличие bank-claim и качество его применения — отдельные вопросы; bank-claim не добавляется принудительно.

`tests/fixtures/llm_profile_quote_regressions.json` помечен как реконструкция по наблюдениям power-trader/metal-borrower/power-software: реальный исходный metal-borrower draft не был предоставлен и не найден в репозитории. Для точной регрессии реального прогона нужен его исходный JSON. Новая диагностика, безопасные снимки, история двух проверок, company isolation и лимит двух вызовов сохранены.
