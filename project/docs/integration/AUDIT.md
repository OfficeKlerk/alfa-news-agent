## `master`

`build.py` нормализует данные и строит базу; `io.py` разбирает CSV, числа, флаги и происхождение; `store.py` возвращает профиль, группы и направления платежей; `signals.py` добавляет объяснимые правила; `profile.schema.json` описывает формат `1.0`. CLI `python -m company_context` позволяет собрать/прочитать базу без HTTP.

Полезные свойства: неизвестные признаки сохраняются как `null`; денежные агрегаты используют Decimal; единица выручки задаётся явно; сохраняются конфликты, номера записей и SHA256 источников; база чтения открывается read-only. Платёжные связи не объявляются поставками, сумма выручки группы — консолидированной, положение в выборке — долей рынка.

Пробел: нет общего API, Docker, CI и интеграции с Node. `test_llm.py` — отдельная ручная сетевая проверка, не офлайн unit-тест. Её не следует запускать автоматически с ключом провайдера.

## `feature/news-analysis`

| Модуль | Ответственность |
|---|---|
| `contracts.py` | Валидация извлечённого события, источников, часового пояса, дедупликация кластера и отсечение будущих публикаций |
| `graph.py`, `features.py` | Направленные платёжные экспозиции, полнота покрытия и объяснимые признаки компания ↔ событие |
| `ranking.py` | Ручной baseline, логистический ranker, разбиения/метрики, происхождение меток |
| `scenarios.py` | Условная оценка сценариев и перебор допустимых действий при наличии параметров |
| `pipeline.py` | `analyze_news`, объяснения, предупреждения и отделение фактов/аналитики банка/оценок |
| `dataset.py`, `evidence.py` | Сборка и проверка датасетов, ревью, карантин, запрет подмены происхождения меток |

Это офлайн библиотека, а не HTTP-сервис, парсер новостей или автономный LLM-агент. Она требует уже нормализованные события с источниками. `score_kind=manual_feature_baseline` имеет собственную шкалу; это не вероятность. Логистический score ограничен 0–1, но не откалиброван как вероятность ущерба. Полноценного проверенного production ML-качества тесты не доказывают. Для реальных моделей нужна отдельная оценка на человеческой разметке; AI-происхождение и ограничения датасетов нужно сохранять.

Выход — `cards/facts/company_evidence/model_assessment/self_check`, а не Node `summary/claims/actions`. Без адаптера эти JSON несовместимы. Сценарные параметры нельзя достраивать из факта наличия кредита или внешнеторгового флага.

Ветка содержит `data/training_v1`, `data/training_v2` и реестры источников/аналитики. Их следует использовать при работе роли 1/3 после проверки применимости; интеграционный PR не переносит многотысячные файлы датасетов в Node-ветку.

## `feature/node-prototype`

| Узел | Реализация и ограничение |
|---|---|
| API/UI | `server/app.ts`, `frontend/*`; `/api`, выбор компании через `X-Company-ID`, фоновые jobs и вопросы |
| Хранилище | `server/db.ts`: собственная SQLite-схема; импорт gzip CSV, источников и demo-новостей |
| Персонализация | `retrieval.rank/feed`: эвристика тем 0–95, упрощённый профиль |
| Новости | `news.ts`: ручной ввод, дедупликация, RSS/Atom из заданных HTTPS-адресов; полноценной классификации сущностей/событий нет |
| RAG | `retrieval.research`: токены + темы, разбиение текста на перекрывающиеся фрагменты; нет векторного индекса, гибридного поиска и отдельного reranker |
| Агент | `agent.ts`, `prompts.ts`, `llm.ts`: планирование tool calls, проверка структуры/источников/цитат, один repair, demo/live, локальные лимиты |
| Исходные инструменты | `get_company_profile`, `search_research`, `find_related_news`; их имена отличаются от целевых `search_news`, `rag_bank_analytics` |
| Запуск | Один Node-контейнер, один volume; прежний Compose требовал `.env`; CI отсутствовал |

`data/research.json` содержит **64 OCR-страницы из 9 документов**, но не содержит полей даты публикации. Это полезная исходная загрузка, не доказательство полноты индекса всех страниц PDF. Для запросов «по состоянию на дату» нельзя выводить даты из имени файла без проверенного реестра. Новый legacy-RAG адаптер исключает недатированные страницы; роль 3 должна связать их с проверенными метаданными.

В Node-проекции неизвестные числа/флаги местами превращаются в 0/false, отсутствует подтверждение единицы выручки. Поэтому она не выбрана источником истины профиля. Node и Python SQLite нельзя направлять на один файл: таблицы, metadata и смысл полей различаются.

## Архитектурные риски и решения

| Риск | Решение в локальной интеграционной ветке | Что остаётся владельцу |
|---|---|---|
| Два профиля и два ranker | `/v1` использует Python; старый `/api` обозначен как переходный | Роль 4 переводит UI на новый SDK |
| Разные форматы события/анализа | Общая JSON Schema/OpenAPI, строгая проверка обеими средами | Роли соблюдают контракты при реализации |
| Блокировка коллег незавершённым сервисом | Общие моки, HTTP-порты замены и native-адаптеры | Поочерёдно заменить моки реальными сервисами |
| Потеря доказательств при генерации | Реестр источников, проверка ссылок и дословных цитат, разрешение дополнительных источников агента через роль 3 | Семантическая проверка фактов и качество извлечения |
| Незаметная подмена baseline вероятностью | Явный `score_kind`, собственная шкала baseline | Оценка и калибровка ML — роль 1 |
| Будущие публикации и неизвестные даты | `as_of`, строгие timestamps, исключение недатированных bank-фрагментов в анализе | Исторические профили и достоверные даты — роли 1/3 |
| Конфликты в общих файлах | Изолированные адаптеры и таблица владения | Изменения контрактов проходят review роли 5 |

`as_of` ограничивает публикации новостей/аналитики. Профиль компании остаётся текущим загруженным snapshot с указанным происхождением: историческое состояние бизнеса на `as_of` не восстановлено. Сквозные тесты подтверждают совместимость, не истинность новостей, качество OCR или точность бизнес-прогнозов.
