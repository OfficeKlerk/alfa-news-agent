Это сохранённая модель продукта, не личное избранное каждого сотрудника. Если нужна личная история/избранное, добавить owner/sub во все соответствующие ключи, запросы и cursor до такого обещания пользователям.
4. OIDC login и возврат после входа учитывают `/live/`; UI перенаправляет на вход после 401. До выбора компании UI получает только runtime-флаг, без общего status. Защита Host от DNS rebinding остаётся в незащищённой локальной разработке и не ломает HTTPS proxy при OIDC.
5. Внутренний credential передаётся gateway → ML/retrieval/agent, включая budget/status. Сохранён длинный timeout для RSS refresh и короткий для обычных запросов.
6. Оба пути генерации, ручной и очередной, используют общий analysis-engine с нашим bank query и проверкой реального контекста. Индекс банка инициализируется только при банковском поиске: сбор/поиск новостей не требуют таблицы research и не захватывают лишнюю write-транзакцию.
7. Совмещены локализация утверждений по продуктам/платежам, обратный порядок predicate, отрицания и тире. Дубли сохраняют числа, знак, валюту и порядок; допускается удаление только явных дискурсивных частиц. Числовые временные горизонты запросов не разрешают финансовые прогнозы.
8. Серверные notices остаются в `meta.warnings`, а не в limitations модели; числовые notices дополнительно сохраняются в trace. Вопросы используют фактический компактный provider view с лимитом и неизменяемыми evidence/hash. Тест коллеги на огромную историю обновлён под этот единый предел вместо его отдельного лимита 65 КБ.
9. Восстановлена привязка каждого LLM-вызова к company и purpose через AsyncLocalStorage: вопросы расходуют свой резерв, repair также учитывается. Это важная часть, которую нельзя терять при переносе валидаторов.

## Нерешённый критичный риск перед платной генерацией

Учёт неопределённого usage сохраняет резерв токенов, но **не предотвращает повторную оплату**. `LiveWorker` может повторять исключения, а просроченная аренда running-job возвращает задачу в очередь. После timeout/reset или падения между ответом LLM и записью результата неизвестно, обработал ли провайдер первый запрос. Нельзя считать ошибку транспорта доказательством отсутствия оплаты.

До включения `ANALYSIS_ENABLED=1` нужен долговечный журнал отправок, состояние unknown/reconciliation и запрет автоматического повторного платного POST в неопределённом состоянии; provider request ID/idempotency — при реальной поддержке провайдера. Сохранённый успешный ответ нужно публиковать повторно без новой генерации. Мы не подменяли это временным решением и не заявляем, что existing idempotency queue устраняет неопределённость внешнего вызова. Задача включена в работу исполнителя 2.

## Запуск и границы готовности

Актуальные команды и условия: `deploy/MERGED_RELEASE.md`. Начать с выключенной генерации на командном стенде. Live-карточки и история теперь долговечны в SQLite; старый ручной путь в памяти в live-режиме заблокирован. Не нужно заново разрабатывать очередь и feed.

Для первого VPS: один gateway со встроенным worker (concurrency=1), Python ML, retrieval/collector и agent adapter; сама Qwen вызывается удалённо. Это несколько backend-процессов, не локальная загрузка весов Qwen. Пригодность 2 ГБ ещё нужно измерить на настоящих данных. Один сервер не означает отказ от атомарных leases, миграций и backup. Горизонтальное масштабирование не является условием первого командного стенда.

Реальные IdP/grants, HTTPS, секреты, актуальная база компаний, проверенные источники, работающий backup/restore, суточный прогон, экспертная Qwen-проверка и устранение неопределённых повторов ещё нужны. Интернет-ссылка сама по себе не делает сборку production.
