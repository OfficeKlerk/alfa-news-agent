# Payment context: проверка объединённой копии, 24 октября 2026

Проверена копия `work/integration-payment-review-20261024`: наши изменения и `origin/codex/payment-context` (`05a6cac`), при неизменном `master` (`023070d`). Старая рабочая копия не изменялась. Внешняя LLM не вызывалась; проверки transport используют заранее написанные ответы.

## Находки и исправления

1. **При объединении требовалась пересборка общих контрактов.** Новый Python-профиль использует `provenance.signal_method=deterministic_rules_v2`, которого не было в нашем прежнем сгенерированном schema/OpenAPI. Новый `payment_summary.counterparty_context` мог проходить старую схему как непроверенное дополнительное поле. `contracts/v1/schema.json` и `openapi.json` пересобраны из объединённого генератора и актуальной схемы профиля; это проблема совместной сборки, не утверждение о несовместимости чистой ветки коллег самой с собой.
2. **Формат не гарантировал согласованность агрегатов.** Можно было передать `available=false` с объектами направлений, долю от известных карточек вместо полного потока, несогласованные суммы/счётчики, неверный признак усечения ID. Добавлены одинаковые проверки Node/Python: согласованность availability, полных directional totals, coverage, отраслевых и групповых корзин, уникальности корзин/ID, размера образца ID и долей. При нулевом знаменателе доли должны быть `null`, а не нулём. Допуск сравнения сумм/долей: относительный `1e-9`, абсолютный `1e-12`, чтобы не требовать битового равенства результатов экспорта Decimal в JSON number.
Дополнительное воспроизведение подтвердило ещё две щели при согласованных остальных суммах: известная групповая принадлежность могла превышать покрытие карточками; при неизвестном собственном `GROUP_ID` допускались `same_group/other_group`. Оба случая теперь отклоняются одинаково в Node/Python; добавлены общие adversarial vectors. Последний отдельный прогон после этих исправлений: 5/5 Node payment tests, 4/4 Python payment tests, TypeScript — прошли.

3. **Ошибку выходного агрегата нельзя выдавать за ошибку пользователя.** Семантическая ошибка в Python превращается в `jsonschema.ValidationError`, поэтому действующий HTTP-boundary возвращает `502 CONTRACT_VIOLATION` для некорректного provider output. Node сохраняет разделение 422/502 по направлению проверки.
4. **Метаданные агрегации могли стать основанием бизнес-вывода.** `profileValue` разрешал `counterparty_context.method/scope` как обычные листья. Эти пути теперь отклоняются; статистические поля coverage и распределений разрешены, как и прежде. Пути `evidence`, `limitation`, целые объекты и provenance не становятся бизнес-доказательством.
5. **Промпт не объяснял новый блок.** Добавлены значения `in/out`, полный знаменатель с неизвестной частью, границы coverage, отличие наблюдаемых сумм от затрат/выручки, неизвестность валюты и периода. Совпадение `GROUP_ID` не трактуется как владение, гарантия или финансовый ущерб.

`counterparty_context` остаётся **необязательным**. Старые frozen profiles, примеры и mocks без него проходят проверку. Отсутствие блока не дополняется фиктивными нулевыми данными; прежний `deterministic_rules_v1` остаётся допустимым.

## Прохождение данных

Полный новый блок сохраняется в `prepareContext.input.profile`, каноническом company-source JSON, hash снимка, исходном входе live-генератора и `prepared_input` уточняющего вопроса. Удаление блока меняет hash и нарушает привязку сохранённого follow-up.

Интеграционный `LegacyAgent` использует `ProjectedStore.canonical_profile`, поэтому поле не теряется при адаптации. Старый кеш включает полный переданный объект компании, включая `canonical_profile`; адаптер дополнительно пересчитывает анализ принудительно. В новом UI блок доступен в полном JSON подготовленного контекста и в раскрываемом источнике «Полный профиль компании». Отдельной карточки распределений не добавляли; UI не переписывали.

Проверен конкретный эффект числового guard:

- Лист `/payment_summary/counterparty_context/out/coverage/industry/known_share = 0.3` разрешён. Фраза «В наблюдаемом исходящем потоке доля известных отраслей: 0.3» с указанием нужных листьев проходит grounding.
- «Потери компании составят 0.3» и «Потери компании составят 30%» отклоняются.
- Свободная фраза «Доля наблюдаемых платежей составляет 30%» **тоже отклоняется**: действующий строгий guard не разрешает AI вычислять процент `0.3 → 30` и вводить финансовые числа вне дословной цитаты. Это известное ограничение формулировки, а не отсутствие данных. Числовые значения сохранены в профильном JSON; защиту от выдуманного ущерба ради этой формулировки не ослабляли.

Проверки подтверждают сохранность и согласованность данных, но не истинность причинных выводов или качество ответов внешней модели.

## Какой маршрут использовать

Для новых Python-профилей и `company_event_v2` нужен **`/v1`**, UI **`http://localhost:8000/analysis/`**; технический интерфейс — `/integration`.

Пример запуска после сборки, без внешней LLM и без подгрузки старого обученного артефакта:

```sh
env -u RANK_MODEL_PATH RANK_MODE=news-analysis NEWS_MODULE_PATH=. \
  .venv/bin/python scripts/dev.py --native-providers \
  --context-db /absolute/path/to/companies.sqlite --data-dir data
```

Используется уже существующая база Python; она не перестраивается этим параметром. `RANK_MODE=news-analysis` выбирает настоящий pipeline с текущим baseline `company_event_v2`; простой `scripts/dev.py` без переменной ранжирует в `mock`-режиме. `--native-providers` включает интеграционные адаптеры поиска и агента. **Без `--live` агент остаётся demo**: «Подготовить контекст» безопасно проверяет реальные профиль и ранжирование без LLM; кнопка формирования ответа даёт шаблонный результат, а не настоящий модельный анализ. Для текущей проверки без LLM содержательные условные советы берутся из offline Python pipeline.

Нельзя путать интеграционный **legacy-адаптер `/v1`**, который получает Python-профиль, со **старым `/api`**. Даже при запуске `scripts/dev.py` корневая страница `/` остаётся старым frontend и обращается к `/api → Node Store.company`; она обходит Python и не создаёт новый `counterparty_context`. `npm start`, `npm run dev` и старый launcher также запускают самостоятельный Node-прототип. Default UI и его аналитику в этой работе не меняли.

`scripts/smoke.py` проходит `/v1/companies → /v1/rank → /v1/analyze → вопросы`, проверяет источники, request ID, изоляцию компаний и доступность legacy health. Основной исполнитель дополнил его отдельными проверками знаменателя нового `counterparty_context`, сохранения полного блока в company-source анализа и версии признаков ручного baseline. Дополнительно выполнены три реальные выдачи профиля, три ранжирования и 30 подготовленных контекстов. Для проверки адаптеров с текущим baseline smoke запускается с `RANK_MODE=news-analysis` и `scripts/dev.py --smoke --native-providers`; используются существующие синтетические fixtures, внешних LLM-вызовов нет.
