# Инструкция по разметке релевантности новостей

> Зачем: чтобы метрика качества ранжирования (nDCG/precision) была **защищаемой**, эталон (`labels.json`) должен быть размечен человеком **независимо** от алгоритма. Иначе система проверяет сама себя и метрика завышена. Эта инструкция даёт единые правила, чтобы у всех разметчиков оценки были сопоставимы.

## Что размечаем

Пары «компания ↔ новость». Для каждой пары ставим оценку релевантности 0–3: *насколько эта новость важна руководителю этой компании для бизнес-решения.*

## Шкала (rubric)

| Оценка | Значение | Критерий |
|---|---|---|
| **3** | высоко | Прямо затрагивает ключевой аспект бизнеса компании; ЛПР захочет действовать/разобраться. |
| **2** | заметно | Влияет через понятный механизм, но не критично или требует условий. |
| **1** | слабо | Косвенная связь; может быть важно при стечении обстоятельств. |
| **0** | нерелевантно | Не касается этой компании. |

### Как рассуждать
Смотри на **профиль компании** (отрасль, продукты банка, ВЭД, регион, контрагенты) и спрашивай: *есть ли механизм влияния именно на неё?*
- Новость про ключевую ставку + у компании есть кредиты → механизм прямой → **3**.
- Та же новость, но у компании **нет** кредитов/лизинга/депозитов → механизма почти нет → **0–1**.
- Новость про отрасль компании → обычно **2–3**.
- Новость про регион регистрации → часто **1–2** (операции могут быть в другом месте).
- Новость про прямого крупного контрагента → **2–3**.

### Примеры (из демо-набора)
- U_34911 (экспортёр зерна) × «пошлина на экспорт зерна» → **3** (прямой удар по марже).
- U_4909 (энергетика, без кредитов) × «ЦБ сохранил ставку» → **0–1** (нет кредитной нагрузки).
- U_99262 (дороги) × «курс рубля» → **0** (нет ВЭД).

## Правила честности (важно!)

1. **Не подсматривать в выход ранжировщика.** Оценку ставим по профилю и здравому смыслу, а не «как решила система». Иначе метрика бессмысленна.
2. **Минимум 2 разметчика независимо.** Затем сверить; где расхождение ≥2 баллов — обсудить и согласовать. Так убирается субъективность.
3. **Оценивать значимость, а не тон.** Плохая новость и хорошая могут быть одинаково релевантны (обе важны для решения).
4. **Не знаем — ставим осторожно.** Если механизм влияния неясен, это 1, а не 3.

## Процесс

### Вариант А — простой (CSV, для людей)
1. Открыть `data/demo/eval/annotation_sheet.csv` (18 пар, столбец `relevance` пустой).
2. Каждый разметчик заполняет свою копию (0–3 + при желании `notes`), **не глядя на предсказания системы**.
3. Свести копии, согласовать расхождения → один итоговый CSV.
4. Сконвертировать в эталон:
   ```bash
   python scripts/sheet_to_labels.py --sheet data/demo/eval/annotation_sheet.csv --out data/demo/eval/labels.json
   ```
5. Измерить качество:
   ```bash
   python scripts/run_baseline_ranking.py --database var/context-real.sqlite3 --news data/demo/demo_news.json --out data/demo/eval/baseline_predictions.json
   python scripts/evaluate_ranking.py --labels data/demo/eval/labels.json --predictions data/demo/eval/baseline_predictions.json --k 3
   ```

### Вариант В — через UI обратной связи (адаптивное обучение, уже в master)
Страница `/learning` (`docs/integration/ADAPTIVE_LEARNING.md`) позволяет проверяющему ставить оценку 0–3 прямо по показанному ранжированию; оценка привязывается к `feedback_id` и идёт в переобучение ранкера. Та же шкала и правила честности из этой инструкции применимы. Система уже обеспечивает независимость: gate-группы для проверки качества не участвуют в обучении.

### Вариант Б — трассируемый (JSONL, встроенный в news_analysis)
Для разметки с полным контекстом (признаки, профиль, граф по каждой паре):
```bash
python -m news_analysis prepare-labels \
  --database var/context-real.sqlite3 \
  --company-ids U_34911 U_99262 U_4909 \
  --events <events.json> \
  --as-of 2026-10-23T00:00:00Z \
  --output data/training/pairs.jsonl
```
Выдаёт JSONL со `label: null` и `annotation_context` (event, profile, graph, feature_evidence). Разметчик проставляет `label` 0..3. Этот путь нужен для обучения ранкера (`news_analysis train`), CSV — для быстрой оценки.

## Как расширять набор

Демо — 3 компании × 6 новостей (18 пар). Для более устойчивой метрики добавить ещё компаний (разных отраслей) и реальных новостей, повторив процесс. Чем больше независимо размеченных пар, тем надёжнее число для защиты.

## Текущий статус

`labels.json` в репозитории сейчас — **черновик**, согласованный с логикой сигналов (не независимый). Его нужно перебить ручной независимой разметкой по этой инструкции, прежде чем приводить метрику как результат на защите (см. оговорку в `docs/BASELINE_REPORT.md`).
