# Оценка рабочего поиска банка

Команда оценивает существующие `Retrieval.research` и `LegacyRetrieval.rag/resolve` на настоящем OCR, загруженном в отдельную SQLite `:memory:`. Это офлайн-вызовы тех же классов, что обслуживают `/v1`, без HTTP, модели, сети и рабочей базы пользователя. Алгоритм выдачи не меняется.

## Запуск

Нужны зависимости Node (`npm ci`) и рабочий Python для существующего stdlib BM25-скрипта. Python нужен только для reference-оценки, не для Node retrieval-сервиса.

```powershell
npm run rag:evaluate
```

Если команда `python` недоступна, передать путь своего Python:

```powershell
npm run rag:evaluate -- --python C:\Path\To\Python\python.exe
```

Параметры:

```powershell
npm run rag:evaluate -- --as-of 2026-10-24T18:00:00Z --repeats 3 --out var/retrieval-evaluation
```

Дата должна содержать часовой пояс. По умолчанию зафиксирован указанный `as_of`, а не текущее время: сравнение не должно незаметно менять доступность источников. Выход разрешён в подпапку игнорируемого `var/`.

## Что измеряется

1. `unfiltered_diagnostic`: старый поиск без временного среза, все 64 страницы. Только диагностика; этот режим не включается в рабочий `/v1`.
2. `server_as_of`: действующий адаптер с фильтром дат, 56 страниц / 8 доступных документов в текущем корпусе. Проверяется настоящий запрос `limit=5` против начала пула `limit=20`.
3. BM25 reference пересчитывается существующим Python-скриптом на **тех же 56 доступных страницах**, с теми же 28 запросами. Старый reference на 64 страницах не подставляется как равнозначный.

В каждом режиме две оценки:

- **Окно источников:** первые k фрагментов, которые действительно получит вызывающий код. Несколько результатов могут принадлежать одному документу.
- **Проекция по документам:** первые k разных документов среди фактических 20 кандидатов. Это диагностика разнообразия, не внедрённое изменение выдачи и не полный ранг всех документов.

BM25 возвращает разные документы по лучшей целой OCR-странице; у сервера чанки и другой tokenizer. Сравнивать его напрямую с окном фрагментов некорректно. Даже сравнение на уровне документов не изолирует влияние одной формулы BM25: отличается единица кандидата, глубина и токенизация.

## Разметка и даты

28 запросов размечены по **документам**, не страницам. Нельзя заявлять page-level accuracy из этих данных.

Для `q07/q08` единственная цель — недатированный обзор золота. Они показываются в отчёте как `unanswerable_under_as_of`, а не скрываются. В `q25` одна из двух целей недоступна. Публикуются обе версии метрик:

- `strict_original_labels`: все 28 запросов и все исходные цели, включая недоступные.
- `available_targets_only`: 26 запросов хотя бы с одной датированной доступной целью; недоступные цели перечислены отдельно.

Дата без времени нормализуется тем же кодом, что в serving: конец дня UTC. Неизвестная дата не превращается в начало месяца. Пустая доступная разметка не считается идеальным ответом; при нуле оцениваемых запросов метрики — `null`.

`hit@k` — есть ли хотя бы один нужный документ в окне; `recall@k` — доля нужных документов без повторного подсчёта чанков; `MRR@k` — обратный ранг первого нужного результата с усечением на k. Старый `evaluate_retrieval.py` считает MRR по всей сохранённой выдаче — сравнивать только одинаковое определение/глубину.

## Проверка источников и время

Каждый фрагмент должен буквально входить в исходную OCR-страницу. Для действующего адаптера дополнительно проверяются дата, разрешение того же source ID, равенство текста/URL/страницы и отсутствие unknown IDs. Это механическая трассируемость, а не подтверждение релевантности цитаты или бизнес-вывода.

После одного прогрева на запрос выполняются три последовательных измерения. Записываются медиана и p95. Это SQLite в памяти + поиск внутри процесса; HTTP, разрешение источников, Python subprocess и LLM в эти задержки не входят. Не запускать параллельно сборку/тесты для сравнения задержек. Это не нагрузочный тест.

## Результаты

В `var/retrieval-evaluation/`:

- `evaluation.json`: все запросы, ранги, найденные страницы, хеши фрагментов, время и метрики.
- `eligible-corpus.json`: временный корпус для сопоставимого BM25; содержит OCR, не добавлять в Git.
- `bm25-reference.json`: пересчитанный reference на доступном корпусе.

Хеши корпуса, разметки, serving-кода, evaluator и reference записываются по фактическим байтам запуска. Переносы строк на другой ОС могут изменить byte-хеш; метрики и содержимое следует сравнивать с учётом этого.

Принятый снимок: [JSON](../../data/demo/rag/server_retrieval_baseline.json). Выводы и список промахов: [отчёт](../reports/SERVER_RETRIEVAL_EVAL.md). Набор небольшой, использовался при разработке и не заменяет независимую человеческую проверку.

Проверки самого инструмента включены в `npm test`: повторяющиеся чанки, разные знаменатели, усечение MRR, временная доступность, отсутствие целей, испорченная разметка и неполный reference. Генерация снимка в Git автоматически не выполняется — после воспроизведения нужен осознанный просмотр результатов.
