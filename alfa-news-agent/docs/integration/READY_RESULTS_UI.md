# Интерфейс готовых результатов — передача участнику 1

Ветка codex/ready-results-ui, база master d49ddc2. Меняются только integration/live_ui/*, server/tests/live-ui.test.ts и этот документ. Сервер, схемы и логика LLM не менялись.

## Поведение

- Основная лента показывает готовые карточки выбранной компании/роли. stale, явно неуспешные и чужие по scope элементы не отображаются. Клиент не выполняет новых проверок содержания LLM: граница публикации — серверный /v1/live/feed.
- Новые готовые карточки появляются автоматически. Исчезнувшие из успешного снимка карточки удаляются. Открытые карточки, черновики и положение чтения сохраняются по возможности; поллинг обновляет загруженное окно страниц (до 10 страниц за цикл), а не только первую страницу. При ошибке HTTP прежний успешный снимок остаётся.
- По умолчанию пустая лента: «Готовых выводов пока нет». Подготовка показывается только для подтверждённой running analysis выбранной роли, а не по общему счётчику компании или активности collector.
- Введённый вопрос сохраняется до появления успешного ответа в истории. Pending/failed/unknown ответы не показываются как реплики. Старый диалог не стирается при ошибке чтения/генерации. Текст, job ID и idempotency key переживают перезагрузку в viewer-scoped storage.
- При неопределённой отправке кнопка проверки повторяет тот же key. При unknown операции новый POST не разрешён. Известный terminal failed допускает только явную повторную отправку пользователем как новую операцию; автоматического платного retry нет.
- Подробности отказов, состояние источников и отсутствие модели находятся в журнале. Terminal timeout больше не обещает автоматический retry.
- Исправлена гонка: смена роли до загрузки профиля использует запрошенный company ID.

## Минимальная совместимость API

Новых endpoint нет. Использованы текущие /v1/live/feed, /jobs, /analyses/:id, /questions и /status.

1. Feed.items — только опубликованные успешные карточки с company_id, audience_role, analysis, stale=false. Клиент поддерживает отсутствие поля status (текущий формат) либо status=succeeded/ready. Явные pending/failed/unknown не допускаются в основную ленту. Предпочтительно вообще не выдавать их в feed, а оставлять в jobs.
2. Feed.total (из серверной части PR #40; также поддержан необязательный total_ready) — число готовых карточек с учётом компании, роли, текущих версий и favorites-фильтра. Feed.visible_ids используется как полный список доступных ID для удаления исчезнувших карточек. Feed.running_tasks / has_running_tasks задают подтверждённую активную обработку выбранной роли. Пока этих полей нет, UI честно считает загруженные карточки; при пагинации подписывает «Показано готовых выводов». Агрегат queue.analyses по всем ролям/версиям больше не используется как число карточек ленты.
3. Для правильного индикатора подготовки добавить audience_role в publicJob и фильтровать список по company_id + audience_role. Старый API не передаёт роль analysis job: такие задания видны в журнале, но UI не выдаёт их за подготовку выбранной роли. Question job можно связать с ролью через analysis_id текущей карточки.
4. History — успешные ответы с question, answer/response.data.answer, created_at. Если история содержит также неуспешные записи, у них должен быть явный status: клиент показывает только succeeded/ready. Предпочтительно включить job_id успешного ответа, чтобы однозначно связать одинаковые вопросы. Legacy matching использует question + succeeded job + created_at не раньше начала задания.
5. GET details теперь передаёт audience_role. POST questions/favorite сохраняет текущий контракт company_id + analysis_id в URL, без самовольного добавления полей.
6. Сохранить owner isolation, идемпотентность и запрет слепого retry после возможной оплаты.

Серверные фильтры публикации, независимость задач, актуальные версии/область счётчиков и сохранность диалога остаются задачами участника 1. UI не может доказать бизнес-корректность карточки, ошибочно опубликованной backend.

## Проверка

npm run typecheck; npm run build; node --import ./node_modules/tsx/dist/loader.mjs --test server/tests/live-ui.test.ts.

Тесты выполняют настоящий app.js с локальным DOM/API транспортом: автоматическое поступление/удаление карточек, страницы, ошибки чтения, failed/unknown question, перезагрузка во время POST, одинаковый idempotency key, сохранение успешного диалога, смена компании/роли и viewer isolation. Настоящая модель не вызывается. Визуальная проверка — отдельный локальный fixture-стенд с явной пометкой тестовых данных; production не менялся.

## Обнаруженная проблема размещения серверной части

Во время проверки master обновился до b43e139 (PR #40). В нём 978 файлов добавлены в новую вложенную папку alfa-news-agent/. Корневые server/, contracts/ и integration/ при этом не менялись. Рабочий запуск использует корень репозитория, поэтому серверную работу нужно перенести из вложенной копии в корень отдельным серверным изменением. Эта UI-ветка не исправляет расположение чужой серверной поставки, но уже поддерживает её поля total/visible_ids/running_tasks/has_running_tasks и audience_role в publicJob.
