# Роль 3 — Backend/RAG: план Матвея

> Новые HTTP-контракты роли 3 и подключение отдельного FastAPI/Node-сервиса описаны в [integration/CONTRACTS.md](../integration/CONTRACTS.md) и [integration/TEAM.md](../integration/TEAM.md). Ниже сохранена исходная памятка Node-прототипа.

Твой результат: сервер, который выдаёт агенту достоверно атрибутированные новости и фрагменты банковских материалов. RAG означает: сначала найти подходящие источники, затем дать их модели для ответа. Полезность вывода и сам агент — ответственность роли 2; твоя часть обеспечивает поиск и происхождение информации.

Это план и черновик контрактов. Новые имена инструментов, маршруты и поиск ниже ещё не реализованы и не утверждены командой. Нельзя выдавать этот документ за готовую спецификацию сервиса.

## Что есть и чего не хватает

| Требование распределения | Сейчас | Следующее действие |
|---|---|---|

| Все 9 PDF с метаданными/страницами | 64 OCR-страницы уже в data/research.json; оригиналы по ссылкам | Аудит полноты, даты без догадок, стабильные чанки и индекс; повторный OCR сейчас не обязателен |

| Кеширование, журналы, ошибки | Кеш анализа, jobs, llm_calls и AppError есть | Поисковый кеш/инвалидация, структурированные журналы запросов/импорта и мониторинг с 5 |

processed при RSS сейчас считает обработанные записи, включая уже существующие. Это не число новых новостей. RSS summary может быть неполным текстом статьи. Успешная загрузка не доказывает истинность новости. Теги — правила, а не ML-классификатор.

## Первый шаг: R3-01, договориться о контракте

Согласовать с ролями 2 и 5: Node вместо FastAPI, аргументы инструментов, ответ и ошибки, лимиты, способ вызова (внутренние функции или HTTP) и переход со старых имён. Номера страниц считать от 1. Источник — документ/новость, чанк — найденный фрагмент; их ID различаются.

### Предложение search_news — ещё не реализовано

Вход:

```json
{"query":"ставка и кредитование","limit":5,"include_demo":false}
```

Ответ-конверт:

```json
{"items":[],"meta":{"search_mode":"lexical","corpus_version":"news-v1","warnings":[]}}
```

Для каждого item предложены: id, title, text, url, published, tags, is_demo, score, matched_terms. Внутри сервера даты нормализовать; неизвестную дату помечать явно, не заменять текущей датой публикации. Факты/сущности добавлять только после согласования формата и происхождения. score — поисковая оценка, не вероятность и не персональная релевантность компании.

### Предложение rag_bank_analytics — ещё не реализовано

Вход:

```json
{"query":"влияние ставки на финансирование","limit":5}
```

Ответ-конверт:

```json
{"items":[],"meta":{"search_mode":"lexical","corpus_version":"bank-v1","warnings":[]}}
```

Для каждого item предложены: chunk_id, document_id, title, page, text, source_url, page_url, document_date (null если неизвестна), extraction, score. text для цитирования должен быть связан с неизменённым исходным OCR. Не обещать page_url: если хостинг не поддерживает переход на страницу, возвращать null и отдельно page/source_url. Старый источник не скрывать, дату не выводить только из имени файла без явного правила/проверки.

Общие ограничения: query — непустая ограниченная строка; limit — целое число с согласованным максимумом. Пустая выдача — успешный ответ items:[], а не выдуманные источники. Ошибка валидации отличается от недоступного индекса/провайдера. Для HTTP предлагается 400/503, но маршруты и схема error ещё требуют утверждения. Поисковые запросы не должны сами запускать загрузку произвольного URL.

### Совместимость

Сейчас работают GET /api/research и инструменты search_research/find_related_news. Не переименовывать их вслепую: сначала утвердить новый контракт, добавить реализацию и адаптер, затем роль 2 подключает её и проверяет реестр ID/цитаты. Роль 4 должна продолжать получать рабочий ответ. Наличие старой функции не означает, что новое имя уже готово.

## Последовательность реализации

1. **R3-01:** зафиксировать решение по стеку и контрактам. Результат — согласованная схема, затем код; не наоборот.
2. **R3-02:** надёжно загружать новости. Начать с нормализации текста, URL, дат и fixtures двух RSS/одного HTML. Сетевые таймауты, лимиты размера, допустимые источники и частичные ошибки сохранить. После повторяемого ручного запуска добавить расписание, защиту от наложения refresh и backoff.
3. **R3-03:** проиндексировать имеющийся корпус без повторной массовой OCR. Проверить 9 document_id/64 страницы, выделить стабильные чанки, метаданные и версию. Сделать полнотекстовый baseline и проверочные запросы.
4. **R3-04:** реализовать оба инструмента и интегрировать с ролью 2. Проверить пустую выдачу, невалидный запрос, источник/страницу, устойчивые ID и совместимость старого сценария.
5. **R3-05:** после baseline выбирать embeddings. Согласовать поддерживаемый API/локальную модель, размерности, хранение, лицензию и бюджет. Embeddings вычислять при индексации и изменениях, не заново для всего корпуса при запросе. Объединить выдачи, измерить результат; только потом усложнять reranking.
6. **R3-06:** по мере реализации добавить версионированные кеши, факты/сущности, метрики и структурированные журналы; инфраструктуру согласовать с 5.

Работа начинается с небольшого PR, а не с переписывания всего проекта. Все пункты пока открыты; этот документ не запускает платные вызовы или разработку всех шести этапов автоматически.

## Как понять, что твоя часть готова

- Другой участник запускает её из README без твоего ключа и Python.
- Агент получает новости и источники по согласованному контракту.
- Повторный импорт не создаёт дубли; частичный сбой виден и не уничтожает хорошие данные.
- Все документы учтены, страницы и цитаты восстановимы; неизвестные даты/поля честно отмечены.
- Качество поиска сравнивается на одном наборе запросов; приведены результаты, а не только названия технологий.
- Негативные/интеграционные проверки проходят; кеш меняется вместе с корпусом; ключи не попадают в логи.

Смысловая достоверность вывода остаётся общей оценкой с ролью 2/5. Твоя часть обеспечивает происхождение и качество поиска, а не гарантирует истинность любой статьи или ответа модели.
