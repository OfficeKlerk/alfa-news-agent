## Результат

Исправлены два класса проблем: повторный расход LLM при сбое и общие для сотрудников избранное/вопросы. Добавлена полноценная работа с неопределённым исходом внешнего запроса, постоянным журналом, восстановлением результата и операторской сверкой. Неопределённый исход больше не обрабатывается как обычная временная ошибка с повторным платным POST.

| Проблема | Теперь |
|---|---|
| Worker потерял ответ, хотя провайдер мог его оплатить | `unknown`; только GET состояния; автоматический POST заблокирован |
| Процесс упал после ответа, но до публикации | Сохранённые raw response и результат используются повторно без нового POST |
| Перезапуск изменил дату, профиль или историю повторной попытки | Очередь хранит неизменный снимок; ID связан с хешами входа и настроек; конфликт явно блокируется |
| Несколько процессов одновременно взяли одну операцию | Уникальный шаг и резерв бюджета фиксируются в одной транзакции; lease token защищает публикацию |
| Старый процесс продолжил работу после ручной сверки | Эпоха операции меняется при решении оператора; старое выполнение не может оплатить repair или перезаписать состояние |
| Бюджет кончился между черновиком и repair | Оплаченный черновик воспроизводится; при пополнении лимита отправляется только отсутствующий шаг |
| Ответ без usage, обрыв, HTTP-отказ | Консервативный резерв сохраняется; фактический usage сверяется по исходному call ID; отказ не запускает слепой повтор |
| После отката backup журнал выглядит пустым | Глобальный persistent hold, карантин и сверка потерянного окна до продолжения; отсутствующая запись не доказывает отсутствие оплаты |
| Избранное и вопросы видны коллегам одной компании | Личная область по проверенным `company_id + sub`, включая jobs, status, history, cursors и ключи идемпотентности |
| В браузере другого пользователя восстановились чужие черновики | Отдельный storage по viewer; старый общий storage игнорируется; смена сессии вызывает перезагрузку |

Полный технический порядок обновления, миграции, восстановления и команды сверки: [DURABLE_EXECUTION.md](../integration/DURABLE_EXECUTION.md). Настройки paid-генерации остаются выключенными по умолчанию.

## Изменения кода

- `server/model-execution.ts`: журнал операций/попыток/решений, AsyncLocalStorage для шага, replay, блокировка unknown, конфигурационный отпечаток и fencing по эпохе, закрытие и карантин.
- `llm.ts`, `llm-budget.ts`: единая транзакция отправки/резерва, сохранение provider request ID и полного ограниченного ответа до обработки; отмена HTTP с сохранением неопределённого исхода; исходный бюджетный учёт при replay.
- HTTP/in-process agent и клиент: общий fingerprint, приватный GET операции с внутренним токеном, передача AbortSignal; контракты/OpenAPI обновлены.
- `live-store`, `live-service`, `live-worker`: постоянный execution snapshot, lease/recovery, справедливый обход unknown jobs, явные terminal failures, запрет обхода неизвестного вопроса новым ключом, personal owner и миграция.
- Gateway и live UI: личные выборки и черновики, trusted viewer, видимые unknown/maintenance; unknown не помечен как `retryable` в API.
- `server/tools/reconcile-model.ts`: локальная CLI после сборки, оригинальный ответ / подтверждённое отсутствие обработки / закрытие без повтора / безопасное восстановление. Решения сохраняются с оператором и основанием; утилита не вызывает LLM.
- Добавлены 22 теста относительно master: 21 backend/integration и один браузерный сценарий. Обновлены README, инструкция запуска и статус прежнего списка задач.

Поиск банка, персональное ранжирование, collector, обработка полного текста и предыдущие шесть групп валидаторов сохранены из master. Производственные подмены и генерация демо-ответа при ошибке не добавлены. Тестовые транспорт/ответы находятся только в тестах.

## Миграция данных

Остановить старые процессы, сохранить согласованный backup, обновить gateway и agent одной версией, установить зависимости и собрать. Миграции запускаются автоматически и повторяемо. Старые готовые карточки сохраняются. Company-wide favorites и вопросы без owner остаются в архиве; они не назначаются произвольному вошедшему сотруднику. Новое личное избранное начинается пустым.

Незавершённые отправки старой версии с `attempts>0` переходят в отдельный карантин до сверки. Это сознательная защита от повторной оплаты, а не потеря job. Обычный restart не требует ручных действий. Восстановление **старой копии** требует отдельной процедуры: из backup нельзя узнать, что было оплачено после него.

## Что проверяется на вашем стенде

Реальные Qwen и внешний IdP здесь не вызывались. До публичного запуска остаются эксплуатационные задачи: HTTPS/IdP/секреты/реальные данные, проверенный инфраструктурный backup и восстановление, мониторинг/retention, согласованный paid-прогон и независимая экспертная приёмка. Эти пункты не подменены локальными тестами.

Если провайдер не поддерживает восстановление результата и не может подтвердить отсутствие обработки, автоматически и безопасно завершить такую операцию невозможно: она остаётся unknown либо оператор закрывает её без повтора. Код не выдумывает ответ или гарантию exactly-once. Дневные лимиты вызовов/токенов не называются денежным бюджетом без подтверждённого тарифа/баланса.

Несколько процессов на одном узле могут использовать одну локальную SQLite. Для нескольких серверов потребуется общая транзакционная БД и перенос инвариантов журнала/лимитов; независимые SQLite-реплики не являются поддерживаемым горизонтальным масштабированием.

## Состав архива

Проект лежит **в корне ZIP**: распаковать в отдельный каталог/чистую рабочую ветку от указанного master; зависимости установить заново, выполнить `npm run build`. Внутри — полный проект с сохранёнными изменениями коллеги, текущая инструкция, `delivery-task2/changes.patch`, перечень изменённых файлов, хеши и логи. Нет `.git`, ключей, runtime-баз, node_modules или venv. Для применения только diff можно выполнить `git apply --check delivery-task2/changes.patch`, затем `git apply delivery-task2/changes.patch` на чистом указанном master. Сам архив ничего не пушит и не развёртывает.
