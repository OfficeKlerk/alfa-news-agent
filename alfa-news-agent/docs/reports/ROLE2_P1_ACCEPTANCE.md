## Критерии двух задач

| Требование | Реализация и подтверждение |
|---|---|
| `recommendations` — массив строк | Промпт v4: отдельный однозначный пример, связанный пример с grounding, пустой случай. Объекты отвергаются прежней схемой. |
| `grounding.recommendations` — массив оснований | Ровно `claim_indexes`, `condition`, `required_data`; порядок/длина, условие и missing_data проверяются. Лишние поля grounding отвергаются. |
| JSON Schema при поддержке провайдера | Явный `LLM_RESPONSE_FORMAT=json_schema`; отдельные strict-схемы анализа и вопроса из канонического контракта. В остальных случаях совместимый `json_object`. HTTP-отказ не вызывает платный fallback. |
| Согласованный формат уточняющего вопроса | Общие правила доказательности, отдельная инструкция формата; примеры анализа не включаются в промпт вопроса. |
| Проверки не ослаблены | Все прежние `$defs` контрактов, кроме расширения `Error`, побайтово равны после JSON-разбора. Уникальность, цитаты, источники, числа, условия и запреты на финансовые прогнозы проверяются локально в обоих режимах. |
| Проверенные ошибки полей | До 10 ошибок со стадией, JSON Pointer, правилом, ожидаемым типом и численной границей схемы, где применимо. Не возвращаются произвольные сообщения Ajv и значения модели. |
| Точная причина grounding-отказа | Отдельные пути и причины для цитаты, источника, profile path, индекса claim, условия и required_data; пути вопроса относятся к answer/claim_indexes. |
| Безопасный черновик | До repair записывается структурный снимок в `llm_rejected_drafts`: текст и числа скрыты, неизвестные ключи подсчитаны; нет ключа API, заголовков и исходного промпта. Ограничены глубина, обход и массивы; удерживаются последние 100 записей. |
| Ограниченный repair | Два вызова максимум: исходный и одно исправление. В тестах ошибочные ответы исправляются либо отклоняются с диагностикой; третьего вызова нет. Auth/quota/timeout/refusal/truncation не вызывают слепой повтор. |
| Диагностика доходит до пользователя | Error contract → роль 2 → HTTP client → gateway → SDK и продуктовый `/v1`-адаптер; generation_id, число попыток, стадия/поля, признак сохранения снимка. Успешный repair отмечается в trace. |
| Секреты не отражаются | Правила из allowlist, неизвестные имена скрыты, числовые ключи не выдаются за индексы массива. Негативные тесты с фиктивным секретом проверяют repair, SQLite, ошибки HTTP/SDK и tuning-отчёт. |
| Новые RAG-данные работают с обеими задачами | В обоих режимах реальные reviewed-новости и датированный OCR проходят analysis + question, исправление трёх разных ошибок и окончательный отказ после повторной вымышленной bank-цитаты. |

## Границы результата

Внешняя LLM не вызывалась: тесты подставляют транспорт, но используют реальные схемы, валидаторы, HTTP, SQLite, reviewed-новости и OCR. Механическая корректность протокола и ограниченного отказа подтверждена; поддержка strict JSON Schema конкретным шлюзом и смысловое качество реальной генерации этим не измеряются. Для них сохранены отдельные live-команды и экспертное ревью. Docker в среде проверки отсутствует; контейнерный smoke должен выполнить существующий GitHub Actions job `compose-smoke`.

Гарантия применения относится к указанному master. Изменения, которые команда добавит позже в те же места, могут потребовать нового согласования; установщик сначала проверяет целостность пакета, чистоту дерева и `git apply --check`, а при несовместимости останавливается до записи файлов.
