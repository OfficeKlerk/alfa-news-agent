# Свежесть и разнообразие bank-выдачи (TEAM_TASKS2 #5, роль 3)

> Дополняет оценку корректности ретрива (`SERVER_RETRIEVAL_EVAL.md`, hit/recall/MRR) анализом **того, что реально возвращается**: насколько источники свежие относительно `as_of` и не скучены ли они в один документ. Повод — живой прогон (REPORT2): в demo-кейсе 4 из 5 bank-фрагментов пришли из одного июльского обзора; старый прогноз не равен текущей позиции банка.

## Метрики (модуль `server/integration/retrieval-freshness.ts`)

Считаются на возвращённом **top-5** окне, офлайн, без вызовов LLM и без изменения выдачи:

- **Свежесть** (`freshnessSummary`): возраст каждого источника в днях = `as_of − published_at`; `newest/oldest/median_age_days`; `stale_share` — доля источников старше порога (по умолчанию 90 дней, это **порог отчёта, не фильтр выдачи**); `future_dated` — источники с датой позже `as_of` (не должны отдаваться).
- **Разнообразие** (`diversitySummary`): `distinct_documents`, `max_pages_from_single_document`, `top_document_share` — доля одного (самого частого) документа в окне. Близко к 1 = выдача скучена в один документ.
- **Свежесть vs доступность** (`fresherRelevantAvailable`): существует ли датированный **релевантный** документ свежее самого свежего релевантного, фактически попавшего в окно, — то есть «более свежий обзор был, но не показан».

Даты берутся из корпуса `data/research.json` и нормализуются тем же `normalizePublicationDate`, что и в проде (только явные даты с таймзоной; `as_of` обязан иметь таймзону).

## Базовый замер (до), as_of 2026-10-24T18:00:00Z

Режим `server_as_of`, 26 отвечаемых запросов (`npm run rag:evaluate`):

| Показатель | Значение |
|---|---|
| Средний медианный возраст источников (top-5) | **≈ 85.7 дней** |
| Средняя доля одного документа в top-5 | **≈ 0.57** |
| Среднее число различных документов в top-5 | ≈ 2.73 из 5 |
| Средняя доля источников старше 90 дней | **≈ 0.45** |
| Запросов, скученных в один документ (≥60% top-5) | **17 из 26** |
| Запросов, где есть более свежий непоказанный релевантный документ | 3 |

Вывод: корректность высокая (hit@3 ≈ 0.93), но выдача **систематически скучена и устаревшая** — у большинства запросов больше половины top-5 приходит из одного документа, и почти половина источников старше трёх месяцев. Это подтверждает и обобщает наблюдение из REPORT2 (не единичный demo-случай).

## Как воспроизвести (до/после)

```bash
# офлайн, без LLM; BM25-референс считает Python 3.12
npm run rag:evaluate -- --as-of 2026-10-24T18:00:00Z --out var/retrieval-freshness --repeats 3 --python python
```

Результат — `var/retrieval-freshness/evaluation.json`: секция `runs.server_as_of.freshness_and_diversity_top5` (агрегат) и `freshness_top5`/`diversity_top5`/`fresher_relevant_available` по каждому запросу, рядом с метриками корректности. Сохраняются `as_of`, точные `source_id`, `excerpt_sha256` и `base_commit` — это снимок «до». После изменения ретрива/ранжирования прогнать снова с тем же `as_of` и сравнить агрегат и те же поля по запросам.

## Что с этим делать (рекомендации роли 3)
- Снизить скученность: ограничить число страниц из одного документа в top-k (dedup/квота на документ) — метрика `top_document_share`/`distinct_documents` покажет эффект.
- Учитывать давность при равной релевантности: при сопоставимом скоринге предпочитать более свежий обзор; `fresher_relevant_available` указывает конкретные запросы, где это нарушено.
- Не выдавать старый прогноз за текущую позицию банка на `as_of`.

## Честные оговорки
- **Свежесть ≠ релевантность**, а скученность сама по себе не доказывает худший ответ: это диагностика выдачи, а не замена метрик корректности и не разметка качества страниц.
- Порог 90 дней — выбор отчёта; меняется флагом/параметром, выдачу не фильтрует.
- Метрика на уровне документа/страницы, на 26 демо-запросах с document-level разметкой, без независимого человеческого holdout.
- Анализ ничего не меняет в выдаче, промптах и корпусе (`ranking_changed:false`, `llm_calls:0`).
