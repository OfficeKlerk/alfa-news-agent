# Безопасность AI-компонентов

> ТЗ требует предусмотреть механизмы безопасной работы AI: разграничение прав доступа, защиту чувствительных данных, контроль и журналирование обращений к инструментам и ограничения на потенциально небезопасные действия. Для прототипа достаточно обоснованно описать эти механизмы и показать их место в архитектуре — этот документ их описывает и привязывает к реальным компонентам решения.

## Модель угроз (что защищаем и от чего)

| Актив | Угроза | Где возникает |
|---|---|---|
| Данные компаний (выручка, продукты, платёжный граф) | Утечка, доступ к чужой компании | Профиль, лента, API |
| Общий LLM-ключ (бюджет 500 ₽/день) | Утечка ключа, исчерпание бюджета | `.env`, вызовы шлюза |
| Агент и его инструменты | **Prompt injection** через текст новости/документа | `search_news`, `rag_bank_analytics`, интерпретация |
| Выводы модели | Галлюцинации, выдавание догадки за позицию банка | Блок интерпретации |
| Логи | Утечка секретов/ПДн через журналы | Журналирование вызовов |

## Механизмы и их место в архитектуре

### 1. Разграничение прав доступа (RBAC)
- **Место:** gateway / API-слой (`server/app.ts`, `server/integration/`).
- Запрос несёт идентификатор пользователя и его компанию; доступ к профилю/ленте — только к разрешённым `company_id`.
- В защищённом `/v1` работают OIDC/JWT, доверенные `company_ids`, фильтрация списка компаний и привязка истории к пользователю. Legacy `/api` закрыт. Подробная модель доверия и настройка: [PRODUCTION_ACCESS.md](../integration/PRODUCTION_ACCESS.md). Офлайн-режим `AUTH_MODE=development` явно отключает аутентификацию; его нельзя публиковать. CFO/CEO/казначейство — акценты ответа, а не права доступа.
- Пользователь видит только свои компании; межкомпанийные связи (контрагенты/группа) показываются как обезличенные ID, без раскрытия чужих карточек.

### 2. Защита чувствительных данных
- Данные обезличены (синтетические ID) уже на уровне набора.
- Секреты только в `.env` (в `.gitignore`); в репозитории — `.env.example` с пустым ключом. Проверено: реального ключа в истории git нет.
- Ключ не передаётся в браузерный код — все вызовы LLM идут с сервера.
- Минимизация: в промпт модели кладём только нужные поля профиля, не весь сырой набор.
- Приватность репозитория + доступ жюри (см. `docs/DECISIONS.md`).

### 3. Контроль и журналирование обращений к инструментам
- **Место:** агент (`server/agent.ts`) + gateway.
- Каждый вызов инструмента (`get_company_profile`, `search_news`, `rag_bank_analytics`, …) логируется: какой инструмент, аргументы, время, длительность, статус, usage токенов — с **trace/correlation ID** запроса.
- **В логи не пишем:** сам ключ, тело ответа провайдера, ПДн.
- Журнал вызовов — основа аудита и мониторинга расходов (`scripts/estimate_budget.py`).

### 4. Ограничения на небезопасные действия
- **Инструменты только для чтения**: агент читает профиль/новости/аналитику, но **не выполняет действий** (платежей, изменений, отправок). Нет инструментов с побочными эффектами.
- **Лимиты вызовов и бюджета:** локальный лимит вызовов (`MAX_DAILY_LLM_CALLS`); денежный бюджет контролируется провайдером, распределённого локального рублёвого лимита пока нет; при `Budget has been exceeded` — безопасный отказ, а не повтор вслепую.
- **Лимиты токенов** (отдельные для планирования и финального JSON) + таймаут — защита от зависаний и неконтролируемого расхода.
- **Только разрешённые модели** из списка шлюза; других провайдеров агент не вызывает.

### 5. Защита от prompt injection (специфика AI)
Внешние новости и OCR-документы — **недоверенные данные**, в них может быть текст вида «проигнорируй инструкции и …».
- Контент новостей/документов подаётся модели как **данные для анализа, а не как инструкции**; системный промпт это фиксирует.
- **Проверка обоснованности выхода:** итоговый JSON валидируется; каждый факт должен быть связан с источником (проверка цитат уже реализована — несвязанные утверждения отклоняются).
- Агент **не исполняет** указания из контента (инструментов с действиями нет), поэтому инъекция не приводит к небезопасному действию — максимум к некорректному выводу, который ловит валидатор.
- Источники с некорректным URL/без цитаты отбраковываются (`contracts` требует HTTP(S) и excerpt).

### 6. Честность и трассируемость вывода (anti-hallucination)
- Разделение **факт / позиция банка / вывод AI** в структуре ответа.
- Где нет материала банка — помечаем `bank_position_not_provided`, не выдумываем (см. `news_bank_mapping.json`).
- Каждый вывод связан с источником/признаком (provenance в профиле, JSON Pointer на evidence) — можно восстановить основание (критерий №11).
- `self_check` агента помечает неуверенность (`event_requires_source_verification`, `financial_effect_not_estimated` и др.).

## Сводка «требование ТЗ → механизм → где»

| Требование ТЗ | Механизм | Компонент |
|---|---|---|
| Разграничение прав доступа | RBAC по `company_id` (+ TODO аутентификация) | gateway / app |
| Защита чувствительных данных | секреты в `.env`, обезличивание, минимизация промпта | конфиг, агент |
| Контроль/журналирование инструментов | лог вызовов с trace ID, без секретов | агент, gateway |
| Ограничения небезопасных действий | read-only инструменты, лимиты вызовов/токенов/бюджета | агент, конфиг |

## Остаточные риски (для доработки)
- Полноценная аутентификация пользователей ещё не реализована (прототип).
- Нет пер-пользовательских квот бюджета (лимит общий на ключ).
- Prompt injection снижается, но не исключается полностью — ставка на отсутствие действий и валидацию вывода.
