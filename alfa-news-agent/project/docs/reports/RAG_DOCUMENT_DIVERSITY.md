# Разнообразие банковских документов в выдаче RAG

При ограничении в пять фрагментов несколько страниц одного PDF вытесняли другие документы. Выдача теперь сначала берёт лучший совпавший фрагмент каждого документа в порядке прежнего score, затем заполняет свободные места остальными фрагментами. На одну страницу по-прежнему не больше двух фрагментов. Политика применяется ко всем кандидатам с положительным score, без привязки к тестовым запросам или названиям PDF.

Формула score, границы фрагментов, ID источников и API не изменены. После первого прохода весь список уже не обязан быть отсортирован по score: приоритет разнообразия выше повторного фрагмента. При любом limit получается префикс одного и того же списка. Даты фильтруются до выбора. VERSION старого агента повышена до 2.0.3-node, чтобы прежний кэш не скрывал новое поведение поиска; интеграционный агент и так пересчитывает поиск.

## Ограничения

28 development-запросов уже использованы для диагностики, независимого holdout нет. Разметка проверяет нужный документ, а не релевантность конкретного отрывка. Более разнообразная выдача может вытеснить полезный второй фрагмент сильного документа ради слабого совпадения другого PDF. Доказательство качества итогового анализа и ручная разметка цитат ещё нужны. Это лексический поиск, не векторный RAG и не обучение модели. 100% hit@5 здесь означает хотя бы одну размеченную цель в 26 случаях, а не полную точность поиска: recall@5 ниже 100%.

Сравнение с ID источников, страницами и хэшами: [document_diversity_comparison.json](../../data/demo/rag/document_diversity_comparison.json). Вложенный protocol.ranking_changed=false описывает неизменность алгоритма самим CLI во время замера; selection_changed=true фиксирует изменение выдачи относительно baseline.

## Воспроизведение

Команды из корня проекта:

```powershell
npm run rag:evaluate -- --python C:\Users\tmatv\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe --out var/retrieval-diversity
npm test
npm run typecheck
npm run build
```

Полный evaluation.json создаётся в игнорируемой папке var/retrieval-diversity. Python нужен только для прежнего BM25-эталона в проверке, сервер поиска работает на Node.js. Платных запросов нет. Проверки текущего изменения на master 8b3e88b после слияния PR #20 и #21: 148/148 тестов, typecheck и build прошли. Ветка обновлена без конфликтов; base нового PR — master.
