# Обучение ранжировщика по обратной связи

Локальная ветка `role5/adaptive-learning`. GitHub не изменён. Это развитие интеграционного ML-адаптера: исходные `news_analysis/`, `company_context/`, агент и датасеты не переписаны. По умолчанию обучение выключено. Docker не нужен.

## Что именно учится

Модель учится расставлять новости по полезности для компании. Автоматически подбираются коэффициенты 20 существующих признаков, регуляризация L2 из `0.001, 0.01, 0.1, 1.0` и один из двух методов: исходная логистическая классификация или новое попарное логистическое ранжирование. Попарный метод учится ставить более полезную новость выше менее полезной в одном запросе.

Обучение выполняется небольшими пакетами в фоне, а не после каждого клика. Явная оценка 0–3, пояснение и подтверждение проверки источника поступают от доверенного проверяющего. Клики, ответы LLM, AI-разметка из training_v2 и собственные прогнозы не превращаются в человеческую разметку. Подтверждение проверяющего записывается как заявление пользователя; сервер не может доказать его квалификацию или факт прочтения источника.

Это обучение ранжирования. Ответы LLM, RAG, финансовые сценарии, вероятности убытков и нейросетевые веса агента этим изменением не обучаются. Старый интерфейс `/` продолжает использовать legacy `/api`; новая страница `/learning` работает с Python/Node `/v1`.

## Как происходит автоматическая замена

1. `/v1/rank` сохраняет точные признаки, извлечённые при ранжировании, сведения о событии, источниках, provenance профиля и версию модели. Клиент получает отдельный `data.feedback_id`. Оценки нельзя связать с чужой компанией или непоказанным/будущим событием. `X-Request-ID` остаётся идентификатором трассировки и может повторяться.
2. Проверяющий ставит оценку на `/learning` или через API. Повторы не увеличивают вес примера. Конфликтующие оценки отклоняются, а не перезаписываются молча; спорные случаи требуют отдельного разбора офлайн.
3. Политическая/событийная группа навсегда попадает в train, validation либо gate по SHA-256: примерно 70/15/15%. Общий `Event.split_group_id` объединяет публикации об одном решении/политике; если его нет, используется `event_id`. Группировка должна быть правильной ДО разметки. Одно событие нельзя впоследствии перенести в другую группу. Gate-группы никогда не входят в fit.
4. Раз в 60 секунд фоновый поток проверяет достаточность данных. Минимум: 60 train-оценок, 20 usable validation-оценок и 20 свежих usable gate-оценок. Для gate нужны минимум 10 запросов «компания + as_of» и 10 разных групп событий. Usable-запрос содержит минимум две новости с контрастными оценками: хотя бы одну 0/1 и хотя бы одну 2/3. Одиночные анализы не доказывают качество ранжирования.
5. Кандидаты выбираются только по NDCG@5 на validation. Победитель переобучается на train + validation и сравнивается на свежем gate с baseline и активной моделью. Использованные gate-группы расходуются однократно, даже если кандидат отклонён. Следующая попытка требует новых gate-групп; поздние оценки уже использованной группы не открывают её заново.
6. Для допуска требуется запас улучшения: средний парный прирост NDCG относительно лучшего из двух эталонов для каждого запроса минус `1.96 × стандартная ошибка` должен быть не меньше 0.01. Precision@5 не должна ухудшиться относительно обоих эталонов. Это консервативный рабочий фильтр, а не доказательство статистической значимости: запросы могут коррелировать через события. Для отчёта о качестве нужен ещё отдельный, нетронутый независимый audit-набор.
7. SQLite транзакционно переключает активную версию. Следующий `/v1/rank` подхватывает её без перезапуска. Отклонённая модель сохраняется с отчётом, но не используется. Ошибка обучения сохраняет рабочую версию. Одновременно обучается один процесс; записи обратной связи не держатся заблокированными на время оптимизации.

В режиме обучения реестр начинает с baseline. Веса из предыдущего эксперимента с AI-разметкой автоматически не продвигаются. `RANK_MODEL_PATH` для этого режима нужно убрать: активными версиями управляет реестр.

## Первый запуск: PowerShell из корня репозитория

Нужны Git, Python 3.12 и Node.js 24. Установка и сборка, если ещё не выполнены:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt -c requirements.lock
npm ci --ignore-scripts
npm run build
```

Создайте отдельную базу настоящих профилей из исходных CSV. Команда атомарно заменяет указанный выходной файл, поэтому используйте этот новый путь, а не базу с вашими изменениями:

```powershell
.\.venv\Scripts\python.exe -m company_context build --companies data/appendix_1/df_Uid_data_hack.csv --links data/appendix_1/df_Fid_Uid_link_hack.csv --payments data/appendix_1/df_Uid_payment_hack.csv --database var/learning/context.sqlite3 --report var/learning/context-audit.json
```

Единицы выручки остаются unknown, как в исходном модуле; не угадывайте их для получения более красивых признаков.

Запуск:

```powershell
Remove-Item Env:RANK_MODEL_PATH -ErrorAction SilentlyContinue
.\.venv\Scripts\python.exe scripts/dev.py --learning --context-db var/learning/context.sqlite3 --native-providers
```

Откройте http://localhost:8000/learning. Скопируйте токен проверяющего из терминала в поле страницы. Токен хранится только в памяти страницы. Каждый запуск выдаёт новый токен, если `LEARNING_TOKEN` не задан. `LEARNING_REVIEWER` позволяет задать имя проверяющего до запуска; по умолчанию это `local-reviewer`. Один токен соответствует доверенному локальному проверяющему; это не многопользовательская система авторизации. Режим предназначен для localhost.

Здесь ML использует указанную реальную базу. Остальные Node-провайдеры по-прежнему работают в demo-режиме с учебным контекстом; обучение оценивайте на `/learning`, а не по ответам агента в `/integration`. Синтетические события с `is_mock=true` в обучающие оценки не принимаются.

## Как начать собирать оценки

В другом терминале, из корня проекта, подготовьте незаполненный запрос для компании из исходных данных:

```powershell
.\.venv\Scripts\python.exe scripts/learning.py example --company-id U_35074 --output var/learning/request.json
```

На странице загрузите `var/learning/request.json`. Нажмите «Показать новости для оценки», откройте профиль компании, проверьте первоисточники и извлечённые признаки события. Поставьте оценки и поясните каждую. Если данных недостаточно, пропустите новость. Для новой компании повторите команду с её ID. Для самостоятельных событий передайте JSON `RankRequest` по общему контракту.

Готовый пример содержит 21 реальное историческое событие с извлечением AI, которое требует ручной проверки. Он даёт 15 train-, 2 validation- и 4 gate-группы. Его достаточно для начала разметки, но **недостаточно для порога 10 разных gate-групп**. Нужно добавлять новые реальные события, а не переименовывать старые для обхода проверки. Оценка большого числа компаний по тем же четырём событиям не заменяет разнообразие событий.

Карточки показаны по алфавиту без оценок модели, чтобы уменьшить влияние её текущего порядка на проверяющего. Эти рабочие оценки всё равно не считаются независимым экспертным тестом. Не переносите в них готовые AI-метки.

После накопления данных обучение идёт автоматически, пока процессы работают. Если данных мало, статус `waiting` является нормальным. `promoted` означает замену, `rejected` — сохранение предыдущей версии, `failed` — ошибку цикла. Изменение подхода не гарантирует улучшения на реальных клиентах; автоматическая проверка предотвращает замену на кандидата без измеренного преимущества в этом gate.

## API обратной связи

Оба сервиса, gateway и Python, публикуют согласованные схемы в `contracts/v1/schema.json` и `openapi.json`.

`GET /v1/learning/status` и `POST /v1/learning/feedback` требуют заголовок `X-Learning-Token`. При выключенном обучении Python возвращает 404. При неверном токене — 403. Пример feedback:

```json
{
  "ranking_id": "значение data.feedback_id из ответа /v1/rank",
  "company_id": "U_35074",
  "ratings": [{
    "event_id": "event-001",
    "policy_group_id": "policy-001",
    "label": 2,
    "reason": "Подтверждённый канал влияния на операции компании",
    "source_reviewed": true
  }]
}
```

Группа должна совпадать с `split_group_id` события в исходном запросе, а при его отсутствии — с `event_id`. Клиент не присылает значения признаков в feedback. Используются сохранённые сервером признаки.

## Статус, версии и откат

```powershell
.\.venv\Scripts\python.exe scripts/learning.py status
.\.venv\Scripts\python.exe scripts/learning.py models
.\.venv\Scripts\python.exe scripts/learning.py rollback --version baseline
```

Откат загружается при следующем запросе и **приостанавливает автоматические замены**. Можно указать ID ранее принятой версии из `models`; отклонённую версию через rollback активировать нельзя. После разбора причин возобновите:

```powershell
.\.venv\Scripts\python.exe scripts/learning.py resume
```

Веса принятой или экспериментальной версии можно выгрузить в совместимый JSON:

```powershell
.\.venv\Scripts\python.exe scripts/learning.py export --version ID_ВЕРСИИ --output data/processed/adaptive-ranker.json
```

События, оценки, отчёты, модели и журнал переключений хранятся в `var/learning/registry.sqlite3`. Перезапуск их сохраняет. Эта папка исключена из Git. Для резервной копии остановите процессы и скопируйте всю папку `var/learning`. Режим обучения не пишет в исходные CSV, датасеты или GitHub. Сохранённые признаки, источники и сведения о компании требуют того же контроля доступа, что и исходные данные.

Записи показа ограничены последними 3000 и 30 днями; принятые оценки и модели не удаляются. Train/validation используют последние полные запросы объёмом до 2000 строк в каждой части, чтобы ограничить CPU и сохранить часть исторического опыта. Слишком большой свежий gate требует офлайн-разбора, а не молчаливого усечения. После аварийного убийства процесса обучающий lock намеренно не снимается автоматически. Только после остановки всех процессов выполните:

```powershell
.\.venv\Scripts\python.exe scripts/learning.py recover --workers-stopped
```

Для отдельного сервиса без общего launcher задайте `LEARNING_ENABLED=1`, `LEARNING_TOKEN` длиной от 32 символов, `CONTEXT_MODE=existing`, `CONTEXT_DB`, `RANK_MODE=news-analysis`, `NEWS_MODULE_PATH` и запустите `uvicorn integration.app:app` на localhost. `LEARNING_DB` меняет путь реестра; тот же путь указывайте CLI через `--database ПУТЬ` **до** подкоманды. `LEARNING_INTERVAL_SECONDS` задаёт период от 10 секунд, по умолчанию 60. Порог допуска не подстраивается автоматически под желаемый результат.

## Проверки и следующий этап

Новые тесты проверяют оптимизацию, допуск/отказ, однократность gate, неизменность разметки, отказ от AI и mock-событий, токен, изоляцию компаний, блокировку параллельного обучения, сохранение модели при ошибке, загрузку без рестарта и откат. Синтетические тестовые оценки доказывают работу механизма, а не рост бизнес-качества. Существующий CI автоматически включает новые pytest- и Node-тесты; Actions на GitHub в рамках этой работы не запускались.

```powershell
New-Item -ItemType Directory -Force var | Out-Null
.\.venv\Scripts\python.exe -m pytest tests/integration -q
npm run typecheck
npm test
.\.venv\Scripts\python.exe scripts/build_contracts.py --check
```

Дальше: независимая разметка несколькими проверяющими, разбор разногласий, новые события и отрасли, отдельная проверка новых компаний, мониторинг по сегментам и дрейфа. Для production понадобятся управление доступом проверяющих, наблюдаемость и отдельный процесс обучения вместо локального потока. Автообучение не заменяет проверку источников и развитие upstream-извлечения: неправильные признаки будут обучать неправильную зависимость.
