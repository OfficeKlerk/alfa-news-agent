# Независимая приёмка live-конвейера

## Статус передачи

На 25.10.2026 проверена мастер-версия `0e6403e0dfb918448493701fb696750551c911bb` и локальные изменения из итогового архива. Архив/коммит реализации коллеги и доступный live-стенд в разговор не переданы. В master есть ручной RSS refresh, импорт, поиск, rank, анализ и вопросы; нет полного постоянного worker → персональный анализ → доставка обновлений ленты. Поэтому **live-конвейер не принят**. Успешные тесты существующих сервисов не заменяют эту приёмку.

## Что передать для начала

Точный commit или архив коллеги, инструкция запуска worker/очереди/БД и миграций, действующий HTTPS-стенд, две обычные учетные записи с непересекающимися компаниями, отдельная admin-учётная запись, разрешённые источники и новости для проверки, согласованный SLA обновления. Нужны также API/SSE/WebSocket контракт ленты, схема item/cursor/revision, политика избранного, повторов, исправленных публикаций и срок хранения истории. Никакого изменения GitHub для передачи не требуется.

## Автоматизированная проверка доступного v1

`scripts/accept_deployment.py` проверяет настоящий внешний gateway. Он не создаёт тестовые новости и пользователей, не меняет роли, не подставляет fixtures при недоступности сервиса. Используйте короткоживущие bearer-токены двух разных пользователей с правами только на свою компанию, без `news_admin`:

```sh
# Задайте ACCEPT_TOKEN_A и ACCEPT_TOKEN_B в секретном окружении.
python scripts/accept_deployment.py \
  --base-url https://ВАШ-ДОМЕН \
  --company-a U_ПЕРВАЯ --company-b U_ВТОРАЯ \
  --news-id ID_РЕАЛЬНО_СОБРАННОЙ_НОВОСТИ \
  --news-url https://ПЕРВОИСТОЧНИК/СТАТЬЯ \
  --generate --out var/acceptance/before_restart.json
```

`--generate` расходует реальные вызовы: один анализ, один вопрос и возможное исправление ответа по существующим лимитам. Без флага проверяются только чтение, rank и preview; это не полная приёмка LLM. Токены не передаются аргументами и не записываются в отчёт. Скрипт запрещает HTTP и redirects, проверяет реальный `meta.mode`, компанию, исходную ссылку, sources, недоступность чужой истории и административного импорта. Выход 2 означает failed/blocked, а не успешное прохождение.

После настоящего перезапуска сервисов повторите команду с `--previous-report var/acceptance/before_restart.json --out var/acceptance/after_restart.json`. Предыдущий анализ должен читаться. Текущий process-local Map этот критерий **не проходит**: после реализации долговечного хранения тест должен стать зелёным без смягчения проверки.

## Обязательные сквозные сценарии после получения реализации

| Сценарий | Критерий приёмки |
|---|---|
| Новая интернет-публикация | Дождаться новой статьи в разрешённом источнике после запуска; без ручного импорта/refresh увидеть сохранённый текст, event, личный rank, вывод и исходную ссылку в UI в пределах согласованного SLA. Зафиксировать published/fetched/processed/delivered и actual latency. |
| Две компании | Одна новость получает разные основания применимости из действительных профилей. Прямой запрос чужого профиля, feed, favorites, item, analysis, questions и подписки отвергается. Проверить подмену path/query/body/header и reconnect с чужим cursor. |
| Новые события и ошибки источника | Не менее трёх новых публикаций из двух независимых источников; временный timeout/429/5xx одного источника не останавливает остальные. Retry ограничен, с backoff; постоянная ошибка видна в monitoring. |
| Повтор и исправление | Повторная доставка статьи не создаёт вторую карточку и второй платный анализ той же версии. Изменённый текст имеет новую версию, перерасчёт и явный revision, без потери старого происхождения. |
| Применимость и источники | Для каждой карточки проверяются профиль, дата, цитата, bank fragment, условные рекомендации; отсутствие данных остаётся неизвестным. Нет будущих/недатированных источников и неподтверждённых числовых выводов. |
| Подписки и избранное | Пользователь выбирает свои источники/темы/новости по согласованной модели избранного. Изменение выбора влияет на выдачу; чужие настройки недоступны. В ленте нет неограниченного роста и повторов при пагинации. |
| Потеря соединения | Закрыть браузер/разорвать SSE или WebSocket, создать новости, подключиться снова. Cursor восстанавливает пропущенные карточки в правильном порядке без дубликатов; fallback работает по явному контракту. |
| Падение worker | Прервать процесс после записи новости, после получения job и после LLM-ответа до ACK. После запуска задачи не потеряны, завершённые версии не оплачиваются повторно из-за простого retry; незавершённые продолжаются/переходят в явную ошибку. |
| Перезапуск и параллельные worker | Данные, grants binding, очередь и cursor переживают restart. Два worker не обрабатывают одну версию одновременно; backend атомарно владеет job/lease и обновляет результат. |
| Сбой LLM и бюджет | 429/timeout/невалидный JSON не создают готовую фиктивную карточку. Pending/error/ready различимы; rate/concurrency/token/cost лимиты общие между worker, повтор не обходит лимит. |
| Нагрузка | Согласовать число компаний, news/min, одновременных подписчиков и бюджет до запуска. Замерить p50/p95 очереди и доставки, рост БД/памяти, backlog и восстановление после всплеска. Без заданных значений нельзя честно поставить PASS масштабируемости. |
| Независимое содержание | Экспертная проверка реальных карточек отдельно от AI-разметки: релевантность, причинная связь, корректность банковской позиции, полезность и отсутствие чужих данных. |

## Правила интеграции с данным архивом

Публичные company-маршруты и подписки проходят через OIDC policy; внутренний worker использует отдельный backend credential, недоступный браузеру. Все ключи результатов, favorite, exposure, cursor и подписки включают company, а для личных объектов — также `sub`. Проверять право до чтения, а не скрывать чужой результат в UI. Не открывать legacy `/api` ради новой ленты. Не отключать production-запрет fixtures/demo для прохождения тестов. При переносе analyses/history в БД сохранить owner+company проверку и существующие контекст/source/hash guards.

Итог приёмки должен содержать commit SHA, конфигурацию без секретов, реальные времена событий, результат каждого сценария, HTTP-логи без профилей/токенов, перечень дефектов и точные пройденные проверки. `v1_flow_passed` скрипта — только один этап; `live_pipeline_signoff` остаётся false до выполнения всей таблицы на реализации коллеги.
