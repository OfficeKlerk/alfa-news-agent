# Защищённый запуск

Для внешнего стенда используйте `compose.production.yaml`. `compose.yaml` и `scripts/dev.py` без `--live` — явно незащищённая офлайн-разработка с fixtures. Их нельзя публиковать в интернете.

## Доверие и права

Gateway проверяет OIDC/JWT. `company_id` в форме, URL, query или `X-Company-ID` — только выбор контекста, не доказательство права. Каждый переданный идентификатор должен входить в подписанные разрешения пользователя. Противоречащие друг другу идентификаторы также отвергаются. Вложенные company-маршруты наследуют ту же проверку; новые маршруты по умолчанию требуют company scope.

IdP должен выдавать доверенные **плоские массивы** `company_ids` и `roles`. Пример claims: `{"sub":"user-123","company_ids":["U_123"],"roles":[]}`. Настраивать эти поля должен администратор IdP/организации; пользователь не должен иметь возможность назначать себе компании через редактирование профиля. `OIDC_COMPANY_CLAIM` и `OIDC_ROLE_CLAIM` меняют имена этих полей. Вложенный `realm_access.roles` нужно отобразить в плоский claim на стороне IdP.

Проверяются подпись RS256/ES256, точный issuer, audience, `sub`, `iat`, `exp`. API bearer-токен должен быть JWT, выпущенным для `OIDC_AUDIENCE`; непрозрачные access tokens не поддерживаются. Browser login проверяет ID token с audience зарегистрированного `OIDC_CLIENT_ID`. Роли CFO/CEO/treasury меняют формулировки, а не доступ.

`news_admin` разрешает общий импорт новостей, refresh RSS и административные learning-маршруты. Для learning дополнительно нужен существующий `X-Learning-Token`. Эта роль не открывает чужие профили и анализы. Обычный представитель компании не должен получать её.

Список компаний формируется из grants, а не из полного каталога. Сохранённый анализ и вопросы привязаны одновременно к компании и `sub` создателя; другой пользователь той же компании не читает личную историю. Чужая компания даёт 403, недоступный анализ внутри разрешённого scope — 404. Legacy `/api` полностью закрыт в защищённом gateway; прямой legacy-сервер отказывается запускаться без явного офлайн-режима.

## Подготовка

1. Установите Docker Compose v2. Для запуска без контейнеров нужны Node 24.13–24.x, Python 3.12, `npm ci`, `pip install -r requirements-dev.txt -c requirements.lock`, `npm run build`.
2. Создайте реальную SQLite-базу company_context из данных организаторов по `company_context/README.md`. Не подставляйте тестовый профиль. Укажите абсолютный путь в `CONTEXT_DB_HOST`; контейнерный пользователь uid 10001 должен иметь право читать файл и родительский каталог.
3. Зарегистрируйте OIDC client с Authorization Code + PKCE S256 и точным callback `https://ВАШ-ДОМЕН/auth/callback`. Разрешите нужный redirect URI и выдачу company/role claims как в ID token, так и в API access token. Issuer и JWKS должны быть доступны по HTTPS с проверяемым сертификатом.
4. Скопируйте `.env.example` в локальный `.env`. Заполните `PUBLIC_BASE_URL` (только HTTPS origin), `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_AUDIENCE`, при необходимости `OIDC_CLIENT_SECRET`, `LLM_API_KEY`, `CONTEXT_DB_HOST`, `NEWS_FEEDS_JSON`.
5. Сгенерируйте **два разных** секрета следующей командой. Один сохраните в `AUTH_COOKIE_KEY`, второй — в `INTERNAL_API_TOKEN`. Не отправляйте их в Git или браузер.

```sh
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"
```

`AUTH_COOKIE_KEY` — ровно 32 случайных байта в base64url; `INTERNAL_API_TOKEN` — минимум 32 символа base64url (рекомендуется та же команда). Один внутренний deployment credential выдаётся только доверенным backend-сервисам. Он не является пользовательским токеном и не принимается gateway вместо OIDC. Компрометация backend-сервиса находится внутри доверенной границы; внешние пользователи не должны иметь доступа к этой сети или ключу.

```sh
docker compose --env-file .env -f compose.production.yaml config --quiet
docker compose --env-file .env -f compose.production.yaml up --build --wait
```

Настройте существующий TLS reverse proxy на `127.0.0.1:8000`. Он должен сохранять исходный `Host` (включая внешний порт, если он нестандартный). Публичный URL обязан совпадать с `PUBLIC_BASE_URL`. Не подменяйте его внутренним контейнерным именем. Пример location для уже настроенного HTTPS server в nginx:

```nginx
location / {
    proxy_pass http://127.0.0.1:8000;
    proxy_set_header Host $http_host;
    proxy_read_timeout 300s;
}
```

Откройте `https://ВАШ-ДОМЕН/analysis/`. Вход `/auth/login` использует настоящий IdP, state, nonce, PKCE. Cookie зашифрована AES-256-GCM, `__Host-`, HttpOnly, Secure, SameSite=Lax. Запись с browser cookie требует точного `Origin`; bearer API не зависит от cookie. `POST /auth/logout` очищает browser session и также требует Origin.

В production нет mock-сервиса. Python читает существующую базу и вызывает настоящий `news_analysis`; retrieval работает с реальными источниками; agent вызывает LLM. Внешний ключ получает только agent. Демонстрационные новости исключаются из production-поиска и source resolution. Gateway отвергает mock-контекст и demo/mock-ответ вместо их выдачи пользователю. После объединения live-конвейер и collector включены; актуальный запуск — deploy/MERGED_RELEASE.md.

## Проверка и эксплуатация

- Публичный `GET /v1/health` проверяет HTTP-доступность зависимостей, не раскрывает профиль и не расходует вызов модели. Это не проверка действительности LLM-ключа или семантики ответа.
- Порты Python/retrieval/agent не публикуются. Прямые data-запросы к ним требуют `X-Internal-Token`. При ручном запуске привяжите private-сервисы к loopback/закрытой сети; OIDC не заменяет сетевую изоляцию.
- OIDC discovery требует доступного IdP при старте; JWKS кэшируются с ротацией. Разрешения в browser session живут не более 15 минут и не дольше ID token, bearer принимается не старше часа. Изменение grants/отзыв не мгновенные; при экстренном отзыве завершите IdP-сессию и ротируйте cookie key/ключи токенов по процедуре IdP. Logout очищает cookie, не отзывает ранее украденный bearer.
- Browser cookie ограничена 3800 символами: слишком большой набор grants явно отвергается, не обрезается. Для широких административных grants используйте bearer API и лимиты заголовков своего proxy.
- OIDC не зависит от process-local login Map и допускает несколько gateway с одинаковой конфигурацией issuer/audience/cookie key. **Ручные transient sessions вне live всё ещё process-local; live-карточки и история уже сохраняются в SQLite**, с TTL и ограничением ёмкости; распределённая лента и долговечная история должны прийти вместе с live-конвейером. Не включайте round-robin между независимыми gateway до переноса этого состояния.
- SQLite BM25-индекс постоянный; первый поиск индексирует корпус, изменения обновляют только затронутые документы одной транзакцией. WAL-базу нельзя совместно монтировать через сетевую файловую систему. Для распределённого retrieval нужен отдельный поисковый сервис/реплицируемое хранилище; это не скрывается за локальным FTS.
- Секреты и профили не включаются в приёмочный отчёт. В production защищайте каталоги состояния и резервные копии. LLM получает профиль по существующей архитектуре; провайдер должен быть разрешён для обработки этих данных.

Протокольные OIDC-тесты с локальным HTTPS IdP проверяют подпись, PKCE, state/nonce, cookie, CSRF и одноразовый code. Реальное внешнее IdP/права организации и live LLM нужно проверить на вашем стенде; они не подменяются тестовыми учетными данными.
