# Командная работа и устройство проекта

> Этот документ описывает исходный Node-прототип. Единые инструкции пяти ролей, новые границы владения и порядок локальной передачи находятся в [integration/TEAM.md](../integration/TEAM.md); запуск — в [integration/START_HERE.md](../integration/START_HERE.md).

Роли отражают присланное распределение команды. Имена участников 1, 2, 4 и 5 пока не указаны. Матвей — роль 3 Backend/RAG. Распределение ниже — границы ответственности, а не утверждение, что работы уже выполнены.

## Как проходит запрос

Браузер → Express API → SQLite / новости / поиск → агент → API модели → проверка → сохранённый анализ → браузер.

- server/index.ts — запуск; config.ts — настройки; types.ts — структуры.
- server/app.ts — HTTP, проверка входа, очередь и ошибки.
- server/db.ts — хранение, импорт, профиль компании.
- server/news.ts — добавление новостей и RSS/Atom.
- server/retrieval.ts — сейчас объединяет две разные области: rank/feed (роль 1) и research (роль 3).
- server/agent.ts — планирование, инструменты, кеш, проверка ответа и вопросы; prompts.ts — инструкции; llm.ts — клиент модели.
- frontend/ — экран и запросы к API.
- server/tests/app.test.ts — общий тестовый файл. Перед правкой согласовывать пересечения; новые тесты можно добавлять отдельными *.test.ts.

Один файл может затрагивать разные роли. Это не повод запретить изменения; нужно заранее описать изменение в задаче. В дальнейшем удобно разделить персонализацию и поиск по отдельным модулям, но такой рефакторинг ещё не выполнен.

## Точки стыковки

1. Роль 1 поставляет профиль/ранжирование, роль 3 хранит данные и предоставляет API. Поиск похожей новости не заменяет персональное ранжирование.
2. Роль 3 возвращает источники и метаданные; роль 2 решает, какие инструменты вызвать и как сформировать вывод. Извлечение сущностей новости относится к 3, генерация бизнес-рекомендаций — к 2.
3. Роль 4 использует действующие маршруты из ARCHITECTURE.md. Не менять поля незаметно: согласовать новый формат и переходный период.
4. Роль 5 утверждает JSON-схемы и порядок интеграции, организует общий запуск, RBAC, CI/CD и оценку. Роль 3 помогает серверными механизмами, но не берёт всю роль 5 на себя.

Важно: «роль 3 в команде» и роли «Финансовый директор/Генеральный директор/Казначейство» в интерфейсе — разные вещи. Последние меняют акценты ответа модели.

## Как отправить текущий проект

Рабочая папка остаётся корнем Node-приложения. Архив и apps/alfa-insight не нужны. Для PR нужна связь с историей общего репозитория: не создавать независимый git init с последующим force push.

1. В отдельную соседнюю папку клонировать общий репозиторий своим аккаунтом. Это технический checkout для публикации, а не новая основная рабочая версия. Создать ветку feature/node-prototype от актуальной основной ветки (по последней проверке master).
2. Сравнить содержимое с текущей папкой. Перенести server/, frontend/, документы, package*.json, tsconfig.json, конфигурацию запуска, .env.example и нужные data/. Разрешить совпадающие имена осознанно. Ничего не удалять в рабочей папке на D.
3. .env, var/, node_modules/, dist/ и резервные архивы не переносить. Перед commit посмотреть git status и git diff --cached. В .env.example ключ должен оставаться пустым, режим — demo.
4. Создать commit и push ветки самостоятельно. Открыть Draft PR: показать полный Node-прототип, описать уже работающий сценарий и известные пробелы. Предложение по замене FastAPI на Express указать явно.
5. Необходимость удаления старого Python-модуля обсуждается в этом PR. Он не нужен нашему runtime; обязательства сохранять две реализации нет. Удаление из актуальной ветки не удаляет историю прежних коммитов. Не удалять работу ребят без просмотра и решения команды.
6. Попросить другого участника запустить demo. После проверки команда делает merge. Автоматических удалений или объединения из этой папки не выполнялось.

До merge участники могут начинать от опубликованной ветки feature/node-prototype; свои PR направлять в неё. После merge — от обновлённой основной ветки и в неё. Если есть чужие незакоммиченные изменения, сначала сохранить их, не использовать reset/force push.

## Как брать задачи

Каждый пункт TASKS.md имеет ID, владельца-роли, критерий готовности и зависимости. Создать GitHub Issue с этим текстом, указать конкретного исполнителя. Один участник берёт одну задачу, пишет «Беру», создаёт отдельную ветку feature/<id-тема>. Эти документы сами не создают Issues и не отправляют сообщения команде.

Перед PR выполнить npm run typecheck, npm test, npm run build; для UI пройти сценарий вручную. Обычная разработка — в demo. В live не устраивать массовых прогонов без согласованного бюджета. В PR описать результат и проверку; изменения смотрит ещё один участник. Авторы отражаются реальными коммитами; выдуманные соавторы не нужны.
