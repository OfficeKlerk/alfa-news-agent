## Что за продукт

Alfa News Agent — новостная аналитика для компаний. Целевое поведение:

1. Постоянно собирать публикации из настроенных разрешённых интернет-источников, сохранять даты, полный доступный текст, версии и ссылки, различать анонс и статью.
2. Загружать фактический профиль компании из CSV/SQLite: отрасль, география, банковские продукты, внешняя торговля, платёжные связи и неизвестные значения.
3. Ранжировать новости для этой компании; извлекать только доступную к дате анализа банковскую аналитику с цитируемым источником/страницей.
4. Получать структурированный анализ от OpenAI-совместимого API; модель по умолчанию в этой версии — `qwen/qwen3.6-35b-a3b`, адрес/модель настраиваются. Не путать название модели с подтверждением доступности тарифа или провайдера.
5. Проверять JSON, ссылки и цитаты, основания персонализации, условия рекомендаций и числовые утверждения; показывать ленту сохранённых выводов со ссылками. Если фактов недостаточно — явные ограничения, без выдуманных прогнозов и demo fallback.
6. Разрешать личное избранное и уточняющие вопросы по сохранённой карточке.

Новостная карточка общая для разрешённой компании/роли, чтобы не оплачивать одинаковый анализ отдельно каждому сотруднику. **Избранное, вопросы, история и черновики личные** (`company_id + доверенный OIDC sub`). Подписка на автоматический подбор остаётся общей для компании/роли; не объявляй её личной.

## Архитектура и режимы

- Python `company_context/`, `news_analysis/`, `integration/`: профиль компаний и ранжирование; отдельный private ML API.
- Node `server/integration/`: gateway с OIDC/правами, retrieval/collector, LLM agent, SQLite-очередь и live worker.
- `integration/live_ui/`: интерфейс `/live/`, чтение сохранённых карточек и периодическое обновление; GET и обновление страницы не должны запускать генерацию.
- `contracts/v1/`: общие JSON Schema/OpenAPI, генератор `scripts/build_contracts.py`.
- `scripts/dev.py`: локальный fixture/demo-стенд. `--smoke` бесплатный и временный; не является production или проверкой настоящего Qwen.
- `scripts/live.py`: реальный контур с OIDC и фактической базой компаний; без `--with-llm` генерация выключена. Требует POSIX (`fcntl`), поэтому Windows — через WSL2/Linux.
- `compose.production.yaml`, `compose.live.yaml`: защищённый полный контур, private backend-порты; HTTPS обеспечивает внешний proxy. Обычный `compose.yaml` — development/demo.
- `server/index.ts` и `/api`: старый standalone прототип. Его платный live-старт запрещён. Не используй его вместо нового live-конвейера.

Запуск production и offline существенно различаются. Недостаточно получить HTTP 200 от demo и назвать это настоящим сервисом.

## Задача 2: что обязательно проверить

Риск был такой: модель могла принять и оплатить запрос, но ответ потерялся; обычный retry worker мог отправить его ещё раз. Решение:

- Постоянный ID операции = scope компании + тип + job/request ID; хеши входа и конфигурации. Неизменный снимок контекста хранится на gateway до отправки.
- Agent SQLite: `model_operations`, `model_attempts`, `model_reconciliation`; raw response и provider request ID, если доступен. Резерв бюджета и отметка отправки в одной транзакции.
- Полный полученный ответ записывается **до** разбора/валидации/публикации; после сбоя используется replay. Draft и repair — отдельные шаги; оплаченный шаг не повторяется.
- `unknown` после потенциальной отправки — запрет автоматического POST. Worker делает только приватный GET состояния. `not_found` после отправки не считается доказательством отсутствия оплаты.
- Общие дневные лимиты вызовов/токенов, company cap и резерв вопросов; при неполном usage/обрыве сохраняется консервативный резерв. Это не денежный лимит без тарифа/баланса.
- Локальный лимит **до отправки** → deferred; отсутствие ключа до отправки → deferred; полный HTTP 429/ошибка провайдера → сохранённый terminal отказ, без автоматического POST. При повторной проверке исправлен признак API `retryable`: provider rejection не выдаётся за локальный бюджетный retry.
- Worker lease/fencing и эпоха операции после ручной сверки: старый процесс не может оплатить следующий repair или перезаписать решение оператора.
- Локальная CLI `node dist/tools/reconcile-model.js`: исходный ответ провайдера, подтверждённое отсутствие обработки или закрытие без повтора; имя оператора, основание и deadline обязательны. Публичной admin-кнопки для обхода нет.
- После отката на старый backup — persistent hold всей очереди и карантин журнала до сверки потерянного окна. Из восстановленной SQLite нельзя узнать об оплате, случившейся после копии.
- Личная область в БД/API/storage, серверный viewer и смена сессии. Старые общие favorites/Q&A сохранены архивно без назначения случайному сотруднику; старые незавершённые отправки с `attempts>0` помещены в карантин.

Нет обещания внешнего exactly-once: подтверждённая поддержка идемпотентности/получения ответа провайдера не заявлена. Неразрешимый unknown остаётся unknown либо закрывается оператором без повтора. Это необходимое корректное ограничение, не повод придумывать ответ/обнулять оплату.


## Одна команда — что именно происходит

`python scripts/accept_task3.py` проверяет версии/зависимости и хеши известных исходников по `delivery-task2/SOURCE_MANIFEST.json`, затем запускает:

1. Генератор контрактов `--check`, TypeScript typecheck и build.
2. Все Node tests, все Python tests, проверку bundled news-модуля.
3. Пять механических reference-сценариев LLM **без настоящей модели**.
4. Проверки реального банковского retrieval и воспроизводимую оценку персонализации на сохранённых данных.
5. Три HTTP smoke-конфигурации: default, Python ranker + legacy adapter, native providers.

Команда чистит у дочерних процессов унаследованные настройки production, устанавливает пустой LLM API key, demo/offline-режим и не включает интернет-collector. Для трёх smoke-сценариев разрешена генерация fixture-ответа в принудительном `LLM_MODE=demo` с пустым ключом; это не включает платную модель. Тесты настоящего HTTP-agent сами создают локальный HTTPS-провайдер с тестовыми ответами и тестовым ключом. Это fault injection, а не production fallback и не настоящий Qwen.

Логи и `REPORT.json` / `REPORT.md` сохраняются в **новый** `var/acceptance/task3/<timestamp>/`. Можно указать новый каталог: `python scripts/accept_task3.py --out var/acceptance/task3/my-run`. Старые результаты не переиспользуются. Код возврата 0 означает только `LOCAL_AUTOMATION_PASS`. Production и экспертная семантика остаются NOT_RUN. Прочитай логи и метрики; не считай успешный exit банковского бенчмарка доказательством хорошего качества.

Авторская последняя ожидаемая база: **476 Node tests и 257 Python tests**, без failed/skipped; одно deprecation-предупреждение Python-зависимости допустимо и описано. Новые независимые тесты могут увеличить количество. Не занижай состав и не игнорируй падения. Текущие логи автора — `delivery-task2/`; старый `verification/` относится к прежним сборкам.

## Независимые сценарии сверх авторского запуска

| Блок | Что сделать | Критерий |
|---|---|---|
| Изоляция компаний | Пользователь A → компания A; B → B; URL/body/query/header/cursor чужой компании | 403/404, чужих профилей/карточек/истории/избранного/jobs нет |
| Два сотрудника одной компании | Разные sub, общая карточка, разные favorites/Q&A; одинаковые client idempotency keys; смена пользователя во вкладке | История/черновики не смешиваются, чужая question job недоступна, контекст ответа содержит только собственную историю |
| Неопределённая отправка | Провайдер принял POST → оборвать ответ/убить процесс → restart и polling | Счётчик POST той же попытки не растёт; unknown виден; GET/refresh не генерирует |
| Полученный ответ | Падение после записи raw response / до publication/ACK | Восстановлена одна карточка/реплика, новый платный POST не сделан |
| Repair | Первый черновик невалиден, второй ответ потерян или локальный бюджет кончился | Draft не оплачен повторно; после сверки lost repair нет третьего POST |
| Лимиты | Локальный cap, отсутствующий ключ, provider 401/429/5xx, отсутствующий/частичный usage | До отправки нет paid attempt; deferred и terminal отказ различаются; unknown reserve не обнулён; provider rejection не помечен retryable |
| Lease/конкуренция | Два worker/agent с одним локальным SQLite; lease истёк; старый worker завершился после сверки | Не более одного POST на шаг, единственная публикация, старый token/epoch не меняет результат |
| Миграция/restore | Реальная старая схема; backup rollback, hold, ошибочная попытка resume при missing journal | Старое не присвоено случайному пользователю; hold переживает restart; unknown не превращён в «не отправлялось» |
| Новости | Повтор RSS, correction, material vs cosmetic change, excerpt/full text, недатированное/будущее событие | Нет ложных дублей/повторной оплаты; изменения и отсутствие полного текста видимы; источники датированы |
| Grounding/поиск | Цитата банка, дата/страница/URL, ложные числа, отрицания продукта, платежи, вопросы | Источники не изобретены/не меняются; неизвестное не превращается в факт; прежние шесть групп проверок сохранены |

Минимум исследуй HTTP-границы, а не только прямой вызов класса. В новых тестах используй контролируемые локальные транспорт/статьи/ключи, но **не меняй production**, чтобы он работал с заглушкой. При платном запросе считай фактические POST, а не только число опубликованных карточек.

Полезные авторские тесты: `server/integration/tests/task2-{execution,http-recovery,maintenance,personal,worker-recovery}.test.ts`, `server/tests/live-ui.test.ts`. Звёздочка/brace в этом тексте — обозначение файлов; универсальная команда запуска уже дана через `npm test`.

## Внешняя часть задачи 3 — после готовности стенда

Без этих входных данных этап BLOCKED: HTTPS URL; тестовые OIDC-учётные записи двух компаний и двух сотрудников одной компании; отдельный admin; настоящая база компаний; разрешённые feeds; operator-доступ к тестовым копиям gateway/agent DB для fault/recovery; явное согласование провайдера и предельного бюджета Qwen. Ключ хранится локально/у deployment, его не нужно передавать нейросети в чат.

1. Проверить реальные HTTPS/IdP/grants, expiry/login/logout, CSRF, закрытые backend-порты и невозможность открыть чужую компанию прямым API. Проверить реальный server-side отказ, не только скрытую кнопку.
2. Подтвердить новую интернет-публикацию → сохранённый полный текст/даты/версии → профиль и rank → очередь → **настоящий Qwen** → сохранённую карточку со ссылкой → обновление ленты без повторной генерации при чтении. Записать ID и время этапов, проверить исправление статьи и отсутствие полного текста.
3. В согласованном тестовом контуре проверить 429/timeout/restart, восстановление raw response, ручную сверку и отсутствие двойного расхода по данным провайдера. Не запускать destructive fault injection на рабочей базе. Операции `supply_response` требуют настоящего ответа провайдера; придуманный JSON не является сверкой.
4. Проверить backup **и восстановление** с процедурами hold/карантина; затем суточный прогон, память/диск/backlog/collector lag и согласованные задержки. Начальная целевая машина — VPS 2 ГБ, один gateway и один worker с concurrency=1; ресурсная ёмкость не доказана одним фактом старта.
5. Получить человеческое экспертное ревью нескольких компаний на одной новости: релевантность, причинность, позиция банка, цитаты, условность рекомендаций, неизвестные данные и отсутствие неподтверждённых числовых прогнозов. AI/reference-разметка не является независимым human holdout. Не выставлять семантический PASS только по JSON-валидатору.

Реальный запуск и безопасность: `deploy/MERGED_RELEASE.md`, `docs/integration/PRODUCTION_ACCESS.md`, `config/live.env.example`, `scripts/live.py --help`. Supervisor запускается с фактическим `--context-db`, опциональным `--env-file`, ключ даётся только агенту; `--with-llm` включать лишь после согласования бюджета. Не заполнять невыданные URL, токены и согласованные SLA выдуманными значениями.

## Важные инструкции и границы

- Техническая схема/миграции/CLI/restore: **`docs/integration/DURABLE_EXECUTION.md`**. Перед любым admin-действием прочитать полностью. Не удалять journal/job и не менять ID для обхода unknown.
- Исходный отчёт автора: `docs/reports/TASK2_DELIVERY_20261025.md`; повторная проверка: `docs/reports/TASK2_RECHECK_20261025.md`.
- Список ролей: `deploy/NEXT_TASKS_3_PEOPLE.md`. Пункты 1 и внешняя часть 3 не считаются выполненными только потому, что задача 2 реализована.
- Несколько процессов **одного узла** используют один локальный SQLite. Независимые копии SQLite, WAL на NFS и несколько серверов не являются готовым горизонтальным масштабированием. Для multi-host нужны общая транзакционная БД и перенос инвариантов journal/budget.
- В ZIP нет реальных секретов, production-баз, node_modules или venv. Production-инфраструктура/доступ провайдера не подменены fixtures.
- Контрольные суммы проверяют соответствие файлов поставке, а не независимое качество или цифровую подпись разработчика. Авторские patch/checksums/отчёты лежат в `delivery-task2/`. Патч уже применён в ZIP — повторно его к этим исходникам не применять.

## Что вернуть пользователю по задаче 3

Создай новый подробный, но без воды отчёт и краткое резюме. Обязательно:

1. Какая поставка проверена: имя и SHA256 ZIP, base commit, состояние SOURCE_MANIFEST, добавленные независимые тесты; ОС/Node/Python и фактические команды.
2. Матрица всех сценариев: **PASS / FAIL / BLOCKED / NOT_RUN**, факты, логи, счётчики POST, времена, причины пропусков. Из отсутствия стенда не делать PASS.
3. Для каждого дефекта: серьёзность, точный триггер/шаги воспроизведения, ожидаемое/фактическое поведение, затронутая область, минимальное доказательство. Не прикладывать ключи/профили/персональные данные.
4. Отдельные выводы: локальная техническая приёмка; реальный end-to-end; безопасность/restore; экспертное качество; готовность к публичному запуску. Эти оценки нельзя объединять в один «всё работает».
5. Приоритетный список оставшихся задач по исполнителям, без дублирования уже проверенной задачи 2. Приложить новые тесты/протоколы локальным архивом, ничего не пушить.

Начни работу с распаковки, определения корня, чтения актуальных инструкций и локального запуска. Задача — получить новый независимый результат, а не подтвердить прежний ответ нейросети.
