## 1. Изоляция данных

`server/integration/access.ts` реализует стандартный OIDC Authorization Code + PKCE S256 на `openid-client`, подписи и JWKS — на `jose`. Проверяются issuer, audience, срок токена, subject и доверенные company/role claims. Нет локальной таблицы фиктивных пользователей, статического универсального логина или принятия произвольного `X-Company-ID` как права доступа.

Проверка выполняется до обращения за профилем/анализом. Все company_id из path, query, body и header обязаны входить в grants; альтернативный регистр маршрута, trailing slash, URL-кодирование, вложенный company path и конфликтующие идентификаторы не обходят policy. Для новых data-маршрутов scope обязателен по умолчанию; исключения перечислены явно для общих публичных источников и административного API. Это не заменяет предметную проверку owner/cursor в будущей реализации ленты.

Каталог выдаёт только разрешённые IDs. Analysis и questions дополнительно требуют `sub` создателя: другой пользователь с доступом к той же компании не получает личную историю. Наличие `analysis_id` само по себе не предоставляет доступ. В роли CFO/CEO нет административной привилегии. Импорт, RSS refresh и learning ограничены `news_admin`; learning сохраняет дополнительный reviewer credential.

Browser session зашифрована AES-GCM, имеет защищённые cookie-атрибуты и ограниченный срок. Мутации с cookie требуют точного Origin; API поддерживает подписанный bearer JWT. Callback проверяет state/nonce/PKCE, повторное использование authorization code отвергается. Ошибка входа даёт явный отказ.

Private Node/Python API требуют отдельный backend credential; клиент не получает его. Production Compose не публикует их порты. Python не запускается в production с fixture-контекстом, mock-ranker или отсутствующим секретом. Gateway блокирует синтетический контекст и демонстрационный ответ; production retrieval исключает seed-новости до применения limit и не разрешает их источники. Legacy `/api` в защищённом gateway закрыт; standalone legacy допустим только в явной офлайн-разработке.

**Эксплуатационные ограничения:** grants не отзываются мгновенно (browser до 15 минут, bearer не старше часа); stateless logout очищает cookie. IdP должен запрещать пользователю редактировать company grants. Private-service credential предоставляет доверенный backend-доступ, поэтому его нельзя выдавать представителю компании. Большие browser grants явно отвергаются по размеру cookie. Настройка и ротация описаны в `docs/integration/PRODUCTION_ACCESS.md`.

## 2. Банковский поиск и персонализация

### Поиск

Новый `server/bank-search.ts` хранит chunks и FTS5-индекс в существующей SQLite. Первый запрос/смена версии строит индекс; следующие запросы используют его повторно. Триггеры фиксируют изменённые source IDs; вставка, редактирование и удаление обновляют только эти документы. Изменение индекса, revision и очистка pending выполняются атомарно; ошибка оставляет предыдущий индекс целым и pending не теряется. Миграции сериализованы транзакцией.

BM25 учитывает текст и заголовок; нормализация ё/е и ограниченные префиксы помогают русским формам. Пользовательские MATCH-операторы не исполняются. Число query terms и размер выдачи ограничены. На одну страницу — не более двух chunks, первые chunks разных документов получают приоритет. Это явное правило разнообразия, не обученный reranker. Предикат даты применяется до выбора результатов; неизвестные/будущие даты не попадают в live RAG. ISO-даты с микросекундами Python корректно приводятся к миллисекундной точности.

ID фрагмента, исходная ссылка, страница и дословный excerpt сохраняются. Source resolution возвращает точно тот же текст и метаданные. Сохраняется проверка, что вся цитата присутствует в OCR-странице. OCR не исправляется по догадке.

`bank-query.ts` добавляет к заголовку текст события и релевантный канал подтверждённых продуктов: например, кредитование или депозиты при событии ставки. В общий поисковый запрос не передаются ID компании, платежи и provenance. Неизвестный/отрицательный product flag не превращается в положительный.

| Метрика реального окна источников | До | После |
|---|---:|---:|
| Hit@1 | 0.6154 | 0.6923 |
| Hit@3 | 0.9231 | 1.0000 |
| Hit@5 | 1.0000 | 1.0000 |
| Recall@5 | 0.9423 | 0.9808 |
| MRR@5 | 0.7609 | 0.8333 |

Корпус: 64 OCR-страницы, 9 документов; на дату проверки доступны 56 датированных страниц 8 документов. Из 28 разработочных запросов у 26 есть доступная релевантная цель. Таблица относится к ним; полные строгие метрики с недоступными целями сохранены в evidence. Документная разметка не доказывает релевантность каждого отдельного chunk.

Наблюдаемая медиана поиска: 12.84 → 2.11 мс; p95: 14.17 → 2.65 мс. Это прогретый in-process SQLite-тест, до — один повтор на запрос, после — три; без HTTP/LLM, не нагрузочный тест и не SLA. Hit/Recall/MRR не зависят от количества повторов. Сохранены хеши корпуса, запросов, индекса, query builder и evaluator.

Ограничения: поиск остаётся лексическим, без embeddings/семантического reranker и полноценной морфологии. Исторический as_of фильтрует доступные документы, но BM25 corpus statistics строятся по текущему корпусу; это не строгий исторический backtest. Для распределённого поиска нельзя совместно использовать SQLite WAL через сетевую файловую систему.

### Персональное ранжирование

Исправлена ложная объяснимость: раньше feature с ненулевым значением и нулевым коэффициентом могла выводиться как причина оценки. Теперь reasons включают только фактические ненулевые contributions. Полный список contributions сохраняется; при нулевых вкладах объяснение явно baseline, без выдуманной персонализации. Когда оценку даёт только свежесть, возвращается `freshness_only_no_company_signal`. Повторное получение профиля в HTTP-обёртке перед исходным ranking pipeline удалено.

`scripts/verify_personalization_current.py` повторно извлекает события действующим кодом, проверяет точное совпадение records с замороженным аудитом и целостность исходных graph bindings. При изменении смысла события он отказывается переиспользовать граф и требует исходную БД. Старые хеши нельзя просто переписать без доказательства эквивалентности. Замороженные labels/weights не меняются.

Подтверждён результат существующего `articles_v2`: NDCG@3 0.9212, Precision@3 0.5556, Recall@3 1.0. **Это сохранение качества текущего v2, не прирост от новых изменений.** Набор — 3 компании × 13 пересказанных событий, 39 AI-оценок, human-reviewed=0. В top-3 остаётся один суммарный элемент с оценкой 0; в curated-проходе — два. Не подтверждены все условия применимости валютных ограничений, резидентства и наличных операций. Без реальных полей и человеческой проверки нельзя честно устранить это подгонкой коэффициентов.

## 3. Повторная проверка шести исправлений

| Проблема | Исправление и защита от регрессии |
|---|---|
| Отрицания продуктов | Утверждения разделяются по самостоятельным subject/predicate; отрицание одного продукта не переносится на другой. Матрица всех семи продуктов, разные префиксы/разделители/порядок; true/false/null сохраняются. Общий predicate и условные предложения проверяются отдельно. |
| Состояния платежей | Входящий/исходящий поток проверяются локально: есть, наблюдается, отсутствует, равен нулю; смешанные состояния не отклоняются из-за соседней части. Противоречие snapshot по-прежнему отклоняется. |
| Ложные дубли | Отказ от нечёткой близости слов. Дубли — точное нормализованное повторение одного kind с сохранением числовой/валютной сигнатуры. Разные годы, суммы, знаки, валюты, сущности, отрицания и порядок действий не схлопываются. Лимиты 8 claims/3 bank claims сохранены. |
| Числовые запросы данных | Число в явном временном горизонте запроса не выдаётся за финансовый прогноз: будущий график, история за последние месяцы, отчёт за предыдущие кварталы. Послабление действует только для missing_data/required_data/текста рекомендации, не для claims, условий и limitations. Денежные суммы, проценты и утверждения о росте/убытках остаются запрещёнными без основания. |
| Серверные предупреждения | Служебные notices перенесены в `meta.warnings`; они не проходят как текст модели и не загрязняют ограничения/цифры при следующем вопросе. Оба интерфейса отображают предупреждения. Число, выдуманное самой моделью в limitations, по-прежнему отклоняется. |
| Контекст вопросов | Provider view передаёт бизнес-контекст и evidence один раз, без повторных копий и audit-only provenance. Проверяются исходные company/event/as_of/role, source content и hash. Бюджет учитывает фактический компактный view и добавленную guidance; слишком большая история даёт отказ до вызова провайдера. Полные исходные evidence остаются у серверных валидаторов. |

Исходный диагноз воспроизведён: 20/20 корректных формулировок приняты. Четыре транспортных сценария генерации проходят за один вызов тестового транспорта, без repair. Дополнительно проверены противоречия, неизвестные значения, изменённые sources, слишком большой контекст и неподтверждённые финансовые числа. Платных вызовов Qwen для этих проверок нет. В `validator-regressions.test.ts` 37 регрессионных тестов, внутри — расширенные матрицы утверждений; count тестов не равен числу входных вариантов.
