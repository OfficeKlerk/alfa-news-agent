# Подбор рабочих настроек модели (TEAM_TASKS #3, роль 2)

> Цель: получить **полный валидный** JSON-ответ модели в согласованное время и с измеренным расходом токенов. Увеличение лимита вывода само по себе готовность не подтверждает — нужна фиксация по нескольким кейсам.

## Что показал реальный прогон (исходная диагностика)

| Лимит вывода | Результат |
|---|---|
| 6000 токенов | Оба ответа **обрезаны** (`finish_reason=length`): весь бюджет ушёл на reasoning, готового JSON нет. |
| 16000 токенов | Черновики получены, но **не прошли проверки** grounding. |

Причина обрезки — у reasoning-моделей (qwen3, deepseek и т. п.) скрытые reasoning-токены считаются в тот же `max_tokens` и расходуются **до** первого токена JSON. Поэтому ключевые ручки — не только размер лимита, но и **бюджет reasoning**, модель и размер контекста.

## Добавленные ручки (`.env`)

| Переменная | Назначение |
|---|---|
| `LLM_MAX_OUTPUT_TOKENS` | Лимит на финальный JSON (было). |
| `LLM_REASONING_EFFORT` | `none\|minimal\|low\|medium\|high` — ограничить/выключить reasoning, чтобы бюджет дошёл до JSON. Пусто = на усмотрение модели. Пробрасывается как `reasoning_effort`. |
| `LLM_EXTRA_BODY_JSON` | Эскейп-хатч для провайдер-специфичных полей тела запроса (shallow-merge). Не может переопределять `model`/`messages`/`stream`. Примеры: vLLM/Qwen `{"chat_template_kwargs":{"enable_thinking":false}}`; OpenRouter-стиль `{"reasoning":{"max_tokens":1024}}`. |
| `LLM_TIMEOUT_SECONDS`, `LLM_MAX_CONTEXT_BYTES`, `LLM_MODEL` | Время, размер контекста, модель (было). |

Разные шлюзы принимают разные поля управления reasoning, поэтому единый «правильный» параметр не существует — рабочую комбинацию выбираем замером через харнес ниже, а `LLM_EXTRA_BODY_JSON` позволяет подставить нужное поле без правок кода.

## Харнес замера

`scripts/tune_model.ts` (`npm run llm:tune`) гоняет **реальный** путь `/v1` analyze по сетке `модель × лимит вывода × reasoning` на нескольких кейсах оценки и фиксирует по каждому прогону: получен ли полный валидный grounded-ответ, задержку, расход токенов (вход/выход) и оценку стоимости в ₽.

- Ключ **только** из `.env` (`LLM_API_KEY`) — не передаётся аргументом и не в чат.
- Изолированная БД вызовов `var/model-tuning/calls.sqlite3` — не засоряет продуктовую историю.
- Жёсткий лимит вызовов `--max-calls` (по умолчанию 12) бережёт бюджет 500 ₽/день.
- Цены берутся из `data/demo/model_prices.json` — **ПЛЕЙСХОЛДЕР**, не официальный тариф (уточнить у организаторов).

### Запуск

```bash
# ключ в .env: LLM_API_KEY=...  LLM_MODE=live
npm run llm:tune -- \
  --models qwen/qwen3.6-35b-a3b,deepseek/deepseek-v4.1-flash \
  --max-output 6000,12000,16000 \
  --reasoning default,none,low \
  --cases rate_borrower,no_rag \
  --max-calls 18 \
  --out var/model-tuning/results.json
```

Флаги: `--models`, `--max-output`, `--reasoning` (`default` = не задавать), `--cases` (из `evaluationCases()`), `--context-bytes`, `--timeout`, `--max-calls`, `--out`.

### Результат

- Таблица в консоли + `var/model-tuning/results.json` (все прогоны, агрегат по комбинациям, поле `recommended`).
- **viable** = комбинация дала полный валидный grounded-ответ **по всем** тестовым кейсам.
- Рекомендация — минимальный `max_output` среди viable, затем наименьшая задержка.

## Рекомендуемая конфигурация

Заполняется из `recommended` после живого прогона:

```
LLM_MODEL=<model>
LLM_MAX_OUTPUT_TOKENS=<N>
LLM_REASONING_EFFORT=<none|low|...>   # если потребовалось
# LLM_EXTRA_BODY_JSON=...             # если шлюзу нужно иное поле управления reasoning
```

Критерий закрыт, когда зафиксированы: модель, лимит вывода, режим reasoning, размер контекста, время и расход токенов — по нескольким кейсам, с полным валидным ответом.

## Честные оговорки
- Харнес проверяет механическую валидность (JSON + grounding), **не** смысловое качество — оно требует ручного ревью (`npm run llm:evaluate -- --live` + `--review`).
- Стоимость — оценка по плейсхолдер-тарифу; заменить реальным после уточнения у организаторов.
- Набор кейсов демонстрационный; для защиты расширить и проверить вторым человеком.
