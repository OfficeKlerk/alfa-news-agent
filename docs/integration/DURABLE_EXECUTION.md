# Надёжное выполнение LLM и личные данные live-ленты

Изменение от 25.10.2026, база master `fa6a7a9f08daf42c87e51dd5b2a1279e67a14766`. Применяется к live-конвейеру и обоим live-адаптерам агента — HTTP и in-process. Старт старого standalone `/api` с платной моделью уже запрещён. Изменения не включают генерацию автоматически.

## Гарантия и граница

Одна логическая операция имеет постоянный job ID, компанию, тип (`analysis` / `question`), неизменный снимок входа и отпечаток конфигурации. Бюджет и отметка отправки фиксируются **одной транзакцией SQLite до сетевого POST**. Полный ответ провайдера сохраняется до JSON-разбора, валидации и публикации. При рестарте полученный ответ воспроизводится; неотправленный шаг repair выполняется отдельно, уже оплаченный черновик не запрашивается снова.

Если провайдер мог принять запрос, но полного ответа нет, операция получает `unknown`. Очередь не выполняет повторный POST: опрашивает приватный GET состояния. HTTP timeout, потеря lease, отмена worker и отсутствие записи в журнале после отправки не доказывают отсутствие оплаты. Полный HTTP 401/429/5xx сохраняется как terminal отказ; он не вызывает автоматическую повторную отправку и не помечается API как безопасный retry. Локальный бюджетный лимит отличается по явному признаку ошибки до отправки. Локальный лимит **до отправки** откладывает работу без расхода вызова. Локально отменённый запрос до резервирования не расходует вызов.

Здесь нет обещания «exactly once» у внешнего провайдера: его документированной поддержки idempotency/retrieval в коде нет. Неподтверждённые заголовки идемпотентности не добавлены. Неразрешимый исход остаётся видимой ошибкой, а не синтетическим ответом. Для продолжения нужна подтверждённая сверка или явное закрытие оператором без повтора. Повторное создание вопроса с новым клиентским ключом не обходит `unknown` этого пользователя.

Схема рассчитана на один узел с локальным SQLite/WAL и несколькими процессами, открывающими **тот же файл** агента. Уникальная попытка и транзакционный бюджет защищают от конкурентной отправки; lease token защищает публикацию. Каждая ручная сверка меняет эпоху операции: старый процесс теряет право оплачивать следующий шаг и перезаписывать решение. Для нескольких серверов нужен перенос этих же транзакционных инвариантов в общую БД. Независимые копии SQLite или WAL на NFS не подходят.

## Хранимое состояние

- База gateway: `live_jobs.payload.execution` — точный вход анализа либо исходная карточка, контекст и личная история вопроса; owner, lease, результат; личные `live_user_favorites`; `live_questions.owner`; миграции и журнал ручных решений.
- База agent: `model_operations` — вход, хеши, состояние и готовый ответ; `model_attempts` — номер шага, хеш payload, call ID, статус HTTP, полный ограниченный по размеру body, provider request ID и deadline; `model_reconciliation` — история решений оператора.
- `llm_budget_reservations` сохраняет полный консервативный резерв при потере ответа/usage. Если usage получен, учёт сверяется по исходному call ID; replay не создаёт новую оплату в локальном учёте. Repair учитывается как отдельный реальный вызов. Действуют общий дневной лимит вызовов/токенов, company cap и резерв вопросов; день — МСК. Это лимиты потребления, не рублёвый лимит без тарифа/баланса провайдера.
- Журнал содержит исходный профиль и ответ. Базы и backup должны иметь тот же контроль доступа, что и профили; их нельзя публиковать в отчётах или Git. HTTP ответа ограничен `LLM_MAX_RESPONSE_BYTES`; постоянный журнал не заменяет политику retention. Нельзя удалять неопределённые попытки для освобождения места.

## Личная область и миграция

Карточка новости общая для разрешённой компании и роли: сотрудники не оплачивают один и тот же анализ каждый отдельно. Избранное, вопросы, история ответов, ключи идемпотентности и cursors привязаны к `company_id + проверенный OIDC sub`. Owner берётся только из серверной аутентификации. Чужие вопросы не попадают в detail, список jobs, status и контекст следующего вопроса. Вопросы одного сотрудника по карточке исполняются последовательно; другой сотрудник работает независимо.

Браузер получает серверный `viewer_key` и использует отдельное локальное пространство для настроек/черновиков. Общий storage предыдущей версии игнорируется. `X-Viewer-Key` выявляет смену пользователя в уже открытой вкладке и вызывает очистку/перезагрузку; он не предоставляет доступ к компании.

Перед обновлением остановить все старые процессы и сделать согласованную копию состояния. Выполнить `npm ci && npm run build`, обновить gateway **и** agent вместе, затем запустить обычной командой из `deploy/MERGED_RELEASE.md`. Таблицы и индексы создаются автоматически транзакционными миграциями; откатывать бинарник без восстановления совместимой схемы нельзя.

Старые company-wide favorites остаются в архивной таблице, вопросы — с `owner=NULL`: их не раздают первому вошедшему сотруднику. Новое личное избранное начинается пустым. Старые незавершённые jobs с `attempts>0` переходят в `unknown / legacy_send_requires_review`; они не возобновляются без сверки. Готовые карточки и старые записи не удаляются. На обычном повторном старте миграция не применяется заново.

## Сверка неопределённого исхода

Утилита локальная, не имеет публичного административного маршрута, сама не обращается к провайдеру и не создаёт ответ. После сборки:

```sh
node dist/tools/reconcile-model.js --database /absolute/agent.sqlite3 --company U_123 --action inspect
```

Она показывает ID, тип, состояние, шаги, provider request ID и deadline. Получить у провайдера исходный ответ либо достоверное подтверждение, что запрос не обрабатывался. Приложить номер обращения/идентификатор и обстоятельства к `--evidence`. Выждать сохранённый deadline; утилита запрещает изменение ещё выполняющейся операции. Job ID и request ID совпадают. Пример для первого шага анализа:

```sh
node dist/tools/reconcile-model.js --database /absolute/agent.sqlite3 --company U_123 --action supply_response --id JOB_ID --kind analysis --ordinal 1 --actor operator-name --evidence 'Provider support case 123: original response matched to request' --response-file /private/original-provider-response.json
```

Нужен оригинальный JSON Chat Completions с `choices[].message.content`, желательно `usage`, до 1 МБ. Контракт и grounding снова проверяются обычным кодом. Утилита не объявляет произвольный текст успешным ответом. Если существует repair-шаг, сверить его отдельно; новая генерация того же исходного шага не выполняется.

Только после подтверждения отсутствия обработки:

```sh
node dist/tools/reconcile-model.js --database /absolute/agent.sqlite3 --company U_123 --action confirm_not_processed --id JOB_ID --kind analysis --ordinal 1 --actor operator-name --evidence 'Provider support case 124: request was never processed'
```

Резерв токенов этой попытки освобождается; сам факт попытки остаётся в лимите вызовов и аудите. Worker прочитает `recoverable` и продолжит с исходным снимком. Нельзя считать отсутствие строки в личном кабинете или просто прошедшее время доказательством отсутствия обработки.

Если результат восстановить невозможно, закрыть операцию без повторного платного запроса:

```sh
node dist/tools/reconcile-model.js --database /absolute/agent.sqlite3 --company U_123 --action close_without_retry --id JOB_ID --kind analysis --actor operator-name --evidence 'Provider cannot recover outcome; operator closes without retry'
```

Worker увидит terminal failed, освободит цепочку личных вопросов и покажет ошибку. Неопределённый резерв сохраняется. Для Q&A указать `--kind question`. Закрытие не является подтверждением отсутствия оплаты. Поздний ответ не перезаписывает решение оператора.

Если новой записи агента вообще нет (старая версия, утрата базы), после документальной сверки **всех** попыток job разрешить продолжение на базе gateway:

```sh
node dist/tools/reconcile-model.js --database /absolute/gateway.sqlite3 --company U_123 --action review-job-not-processed --id JOB_ID --actor operator-name --evidence 'Provider reconciliation of every attempt confirms no processing'
```

Для старой мигрированной job доступна более узкая команда `review-legacy-not-processed`. Разрешение на отправку при отсутствующем журнале одноразовое и потребляется при фиксации snapshot. Если отсутствие обработки не подтверждено, использовать `close-job-without-retry` на gateway; при существующей операции закрыть её и на agent. Нельзя удалять job, менять ID или чистить журнал, чтобы обойти блокировку.

## Backup и восстановление

Обычный restart с сохранёнными актуальными базами не требует ручной сверки. **Восстановление более старой копии** может потерять операции, оплаченные после её создания. Без внешнего журнала/сверки провайдера доказать их отсутствие из самой восстановленной SQLite невозможно.

1. Остановить все процессы deployment. Сделать согласованный backup gateway, agent, retrieval и company DB средствами SQLite backup либо после корректной остановки и checkpoint; не копировать один main-файл работающей WAL-базы. Сохранить актуальную копию до отката.
2. Восстановить файлы в закрытом каталоге. **До старта** поставить глобальный hold очереди и карантин журнала (это операции для всей БД, поэтому требуется `--company ALL`):

```sh
node dist/tools/reconcile-model.js --database /absolute/gateway.sqlite3 --company ALL --action quarantine-restored-queue --actor operator-name --evidence 'Restored backup timestamp and incident reference recorded'
node dist/tools/reconcile-model.js --database /absolute/agent.sqlite3 --company ALL --action quarantine-restored --actor operator-name --evidence 'Restored backup timestamp and incident reference recorded'
```

3. Запустить сервисы с выключенной платной генерацией. Hold сохраняется в БД, блокирует claim, recovery-dispatch и автоматический подбор новых jobs. Чтение карточек и сбор источников отдельным collector остаются доступны; UI показывает остановку на сверку.
4. Сверить провайдера и доступный актуальный журнал за **всё потерянное окно**, включая отсутствующие в backup jobs/резервы. Неотправленные восстановленные jobs разрешать только по подтверждению; неопределённые закрывать без повтора. `restore_review` агента намеренно не оживляется по одной старой попытке: дополнительные попытки могли исчезнуть при откате. При недостатке доказательств закрыть без повтора. Перед снятием hold нужно восстановить учёт и перечень уже оплаченных/завершённых операций из актуальной копии; если этого сделать нельзя, продолжать с hold, не запускать слепой повтор discovery.
5. После полной сверки снять hold с аудитом:

```sh
node dist/tools/reconcile-model.js --database /absolute/gateway.sqlite3 --company ALL --action release-restored-queue --actor operator-name --evidence 'Lost backup window reconciled with provider and current journal; accounting restored'
```

Снятие hold не переотправляет unknown jobs. Они требуют описанного решения по конкретной операции. Процедуру проверить на реальном deployment; автоматические тесты проверяют сохранение hold, fencing и запрет dispatch, а не сохранность инфраструктурного backup.

## Проверки

`npm test` включает реальные SIGKILL дочернего процесса до/после сохранения ответа, рестарт, конкурентные экземпляры агента, отдельный repair, локальные лимиты, отмену, HTTP-отказ и ручную сверку. Интеграционный тест поднимает настоящий provider-server и локальный HTTPS Chat Completions endpoint: потеря ответа после принятия POST → unknown → оригинальный ответ → replay после рестарта без второго POST. Проверен и полный путь очереди через production AnalysisEngine/HTTP-agent до публикации сохранённой карточки после сверки без второго POST. Endpoint и ключ исключительно тестовые, production не имеет этой подмены.

Проверяется также HTTP-изоляция двух сотрудников и другой компании, подмена owner/header, личная история при генерации, cursor, миграция прежней схемы и браузерные черновики. Для локальных HTTPS-тестов нужен `openssl`. Настоящий Qwen не вызывается; живую сверку с вашим провайдером и ограниченный paid-прогон выполнять отдельно с согласованным бюджетом.
